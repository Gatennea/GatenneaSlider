# 特大尺寸求解期「短暫無響應」測帧定位（2026-11-16）

> 對應待辦 §四十三（用戶原話：「特大尺寸求解过程中有可能短暂无响应」，
> 補充「特大 = 超过 10×10、等级 2」）。本輪只做**先量後改**：先量出停頓落在
> 哪一段，再把量到的三處熱點裡可安全收口的兩處落地；剩下的一處（GIL）寫清
> 結論與下一步，不動求解器架構。

## 0. 結論摘要

12×12、step=2、混合求解（hybrid）無頭實測：

| 指標 | 改前 | 改後（思考演示開） | 改後（思考演示關） |
|---|---|---|---|
| 單次「找一步」最壞 | **13 700ms**（全量枚舉兜底） | 12.9ms（預算封頂） | 同左 |
| 單次「找一步」均值 | 38~70ms（取樣路徑） | 11.9ms | 同左 |
| 幀間隔均值 | 45.5ms | 33.4ms | 27.5ms |
| 幀間隔最大 | 194.5ms | 125.8ms | 97.4ms |
| ≥100ms 帧數（25s/20s） | 55 | 6 | 0 |
| 空闲基線幀成本 | 18.4ms | 18.0ms | 17.3ms |

三處根因：

1. **全量枚舉兜底（已修）**：取樣「3 塊 × 6 縫」全不合法時退回
   「塊 × 縫 × 方向」全枚舉；12×12 塊數 144、縫 44，單次 **13.7s**。這是
   「整窗無響應」的直接原因。取樣全不合法在大尺寸上很常見——隨機在全盤抽
   塊，絕大多數落在同一大片裡，引擎判「整盤平移」直接拒絕。
2. **選步成本按面積增長（已修）**：即使不走兜底，固定取樣規模在 12×12 也要
   38~70ms/步；另一頭是聚攏度打分 `gather_metrics` 單次 1.26ms × 全部候選
   （24 個 ≈ 30ms）。游走每步都掉幀。
3. **後台求解搶 GIL（未治本）**：同一段 `draw_status_bar` 單獨跑穩定 **0.2ms**，
   在求解期間的循環內量到 **10.9ms**——差的那 10ms 是等 GIL，不是真 CPU。
   後台求解是純 Python CPU 密集線程，主線程只能搶時間片。治本＝求解搬獨立
   進程（`docs/api/API缺陷与改进建议.md` A1/A2 早有此建議），代價是快照 /
   進度 / 段跨進程通信，本輪不動。

## 1. 測量方法（可複現）

`experiments/script__probe_big_stall.py`——**只讀探針，不改產品代碼**：

- 無頭（`SDL_VIDEODRIVER=dummy`）+ 真實主循環 `GUI.run()`，把 `pygame.time.Clock`
  換成逐幀計時的假時鐘（保留 60fps 節奏），每幀記帧間隔；
- 第 20 幀啟動一次真實 hybrid 求解，到時取消、再跑 180 幀收尾；
- 逐幀按「思考演示 / 段播放 / 後台搜索等待 / 空閒」粗分類，輸出各類最大、
  均值與最慢 12 幀明細；
- 另單獨給 `_think_find_move`（含最壞分支）計時；
- `--breakdown 1` 會包一層幀內分段計時（handle_events / update_animation /
  draw_board / draw_status_bar / flip …），用來看每帧時間流向。

跑法：

```bat
D:/python/python.exe -u experiments/script__probe_big_stall.py --m 12 --n 12 --step 2 --moves 40 --seconds 20
D:/python/python.exe -u experiments/script__probe_big_stall.py --m 12 --n 12 --step 2 --moves 40 --seconds 20 --breakdown 1
D:/python/python.exe -u experiments/script__probe_big_stall.py --m 12 --n 12 --step 2 --moves 40 --seconds 20 --think 0
```

避坑兩條（探針已處理，寫在這裡防覆轍）：

- dummy 視頻驅動建不了系統光標，真實主循環每帧抛
  `Error while creating system cursor`，**120 帧連續異常後主循環自我終止**
  （現象是「一帧都沒採到」）。探針把 `_update_cursor` 置空。
- `SliderMatrix` 有 `__slots__`，實例上掛不了 `try_move` 包裝；要數引擎調用
  得包**類方法**（見 `test/_test_think_select_budget.py`）。

## 2. 已落地改動

### 2.1 思考演示選步：縫線鄰塊 + 牆鐘預算（`gui/auto_solve.py`）

- 常數：`THINK_SELECT_BUDGET_MS = 6`（枚舉）/ `THINK_SELECT_MAX_CANDS = 24`
  / `THINK_SCORE_MAX = 3` / `THINK_SCORE_BUDGET_MS = 5`。
- 只抽**縫線兩側鄰塊**（方形：塊跨 `[r, r+step-1]`，上鄰 `r = line-step+1`、
  下鄰 `r = line+1`；異形用字母族縫，退回隨機塊）。這群塊才是「縫切出來的
  連通片」，命中率接近 1。
- 有界兜底：鄰塊為空（異形 / 不規則盤面 / 假引擎）時，小盤（≤12 塊）全掃、
  大盤再抽 3 塊；**仍受同一預算與候選上限**。找不到就返回 `None`，狀態機下
  一帧換一批再來——不卡死、也不退回全枚舉。
- 打分只對 3 個候選做，且第一候選無條件打分（保證 `scored` 非空），其後到
  5ms 預算即停。

### 2.2 狀態欄文字緩存（`gui/renderer.py`）

- 新增 `_status_text_surface(text, color)`：按 `(字體對象 id, 文字, 顏色)` 緩存
  渲染結果，上限 96 條滿則整批清。
- 狀態 / 引擎 / 謎題 / 縮放四段基本恆定，只讓真正在變的步數 / 計時 / 宏進度
  重渲染。單獨量測：整條狀態欄 **3.4ms → 0.2ms**（穩定態）。
- 註：求解期間循環內的 10.9ms 主要是等 GIL（見 §0.3），緩存只收掉了真 CPU
  那一截。

### 2.3 護欄

- `test/_test_think_select_budget.py`（新增）：12×12 真盤面 10 輪，鎖三條契約——
  單次選步 ≤300ms、`try_move` ≤80 次（舊全枚舉是千次量級）、且 ≥8/10 輪仍
  能找到走法（預算不能靠「永遠找不到」實現）。實測穩態 **9.3ms/輪**。
- `test/_test_think_walk_selection.py`：只把「退回全量枚舉」的舊措辭改成
  「有界兜底」，斷言不變。
