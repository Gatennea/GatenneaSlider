# UI 實現鐵律（視覺一致 / 開關哲學 / 事件分發）

> 2026-11-06 從 `agents.md` §3 / §15 / §16 拆出（內容未改，只加交叉指引）。
> `agents.md` 只留一行紅線 + 指針；細節與「為什麼」都在本文。
> 相關：`docs/ui/前端動效優化計劃.md`（做什麼）、`docs/spec/術語規定.md`（怎麼說）。

## 1. 三形態同時生效（視覺反饋鐵律）

- 任何視覺反饋 / 動效必須 **square / tri / mi 三形態同時生效**：一處 shared helper + 三個 draw
  （`draw_board` / `draw_triangle_board` / `draw_mi_board`）各接一次。寫一個 ≠ 三種都有；
  驗收走 `test/_check_gap_annot.py`。
- **不給滑塊引入新的填充色表達狀態**（撤銷藍填充被否）；換邊框顏色 + 加粗，保留 `be_opted`
  提亮這個原始特色。
- `DIRECTIONS` / `GAP_DIRECTIONS` 是**模組級常量**，不是 game 實例屬性（`getattr` 拿空 dict
  會靜默退化）；按形態從模組取。
- **不維護「方向字母 → 屏幕向量」表**（三角 `'w'` 與米字 `'w'` 屏幕朝向不同）；正確做法 =
  `game.DIRECTIONS[d]` 格增量 + 形態自己的 view 反算屏幕差。
- 動效總開關 `ui_mode ∈ {plain, enhanced}`（默認 enhanced，`config.json` 持久化）；plain 走舊行為，
  S1~S7 增強僅在 enhanced 插入。
- 求解進度**不做百分比進度條**（無法保證成功 / 估算時長）；改「統一容器不統一內容」狀態卡：
  狀態 + 階段名 + 活動指示 / 已用秒數 + 已探節點數 / 求解器自報指標。

## 2. 控制與開關的設計哲學（用戶定，勿擅自改）

**核心原則：好的控制設計，既允許「鼠標 + 鍵盤」流暢操作，也允許「只用鼠標」完成一切操作。**
任何「鍵盤能做、鼠標做不到」的遊戲內功能都算缺陷（外部 HTTP API 不算數，那是另一條通道）。

- **五種操作方式**：單次觸控 / 兩次觸控 / 鼠標鍵盤 / 虛擬鍵盤 / 箭頭按鍵。
  五種各有獨立開關，可任意組合；宣傳口徑與設置界面必須對得上（說五種就得有五個開關）。
- **開關放哪裡，只看使用頻率**：
  - **右下角快捷區**＝**遊玩中需要經常切換**的開關（顯眼位置，一鍵就到）。
  - **設置對話框**＝**不常改變**的東西（收回設置，不佔常用區）。
  - 判據實例：視覺增強類（着色 / 連鎖 / 棋盤標記）屬「常用」——一局之內
    前期嫌晃眼不想開、後期要數格子又必須開，會來回切，故放右下角；
    逆序播放宏本人用不上，故從右下角撤回設置。
- **鍵鼠對等的已知補丁**（做過就不要退化）：
  - 三個懸浮面板 F1 虛擬鍵盤 / F2 調試面板 / F3 成績目錄都要有純鼠標入口
    （成績面板原先只能靠 F3，已在右下角補「成績」開關）。
  - 求解器任何入口都要能在選了算法後由 Ctrl+A 觸發；**不要為單個算法開專用
    快捷鍵**（Ctrl+G 單段求解就是這樣爛尾的——已改稱「選塊填空」收編進列表）。
  - 競速模式開始計時 / 放棄原本只有空格，已在狀態欄計時區補可點區域。
  - 新增功能時先自查：「只用鼠標的使用者能不能做到？」

## 3. UI 事件分發紀律（踩過事故）

- **對話框底部的「確定 / 取消 / 恢復默認」必須最先判定**，命中即返回。
  各 Tab 的選項行是橫貫整寬的大矩形，列表滾到底時會蓋到按鈕區；先判選項行
  會讓「確定」被截獲 → 算法被悄悄改掉、對話框還關不掉（用戶實測的
  「選 A 算法卻切到 B」就這麼來的，且表現像隨機）。
- 開關狀態要寫進配置（`config.json`）與遠程白名單（`_SETTINGS_BOOL_KEYS`、
  `http_server` 同名表），新增開關時三處一起加，別漏。
