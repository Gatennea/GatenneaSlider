## 0. 共識與邊界（先讀）

### 已確認要做
| 項 | 用戶態度 |
| --- | --- |
| 撤銷走冷色 / 重做走暖色 | 「很好」 |
| 聚攏度做成盤面外圈的弧，每步增亮 | 「很好」 |
| 先處理事件再繪製（省一幀輸入延遲） | 「沒感覺，這個可以做」 |
| 三種棋盤線條粗細、圓角統一 | 確認要做 |
| 音效（BGM + 摩擦聲 + 提示音） | 用戶自己提供素材 |

### 不做（已拍板）
- **整片滑塊高亮是從最開始就設計的特色，不改。** 不改成「只描邊」、不改成外輪廓。
- **不做百分比進度條。** 求解無法保證成功、也無法估算時長，畫一條走不到頭的進度條比沒有更糟。
- 滑動曲線（三段式 + 微過衝）**降為可選**：用戶體感上沒有「不像手推」的問題，放在 S7 之後再說。

### 兩條硬約束
1. **棋盤上不加常駐的呼吸 / 流光**。這是空間推理遊戲，持續運動的亮色會和玩家的思考搶注意力。
   常駐動效一律低頻、低對比；一次性事件（復原、失敗）才可以隆重。
2. **動效不能拖慢連播**。35 步的解，每步多 100ms 就多 3.5 秒。求解演示的動效預算要單獨算。

### GUI 模式開關（架構決策，最先落地）
用戶建議：**保留舊版樸素的 GUI，本計劃的動效 / 視覺優化做成一個開關**。
→ 整個 S1–S7 都是「增強模式」才有的東西；關掉開關就回到當前樸素版。

**開關設計**
- 一個總開關 `ui_mode ∈ {plain, enhanced}`，**默認 `enhanced`（建議；這點待你拍板，
  若想默認樸素則改成 `plain`）**。

  加入 `gui/events.py:1249` 的持久化 key 列表（與 `animation_enabled` 同機制）；
  在設置對話框（`events.py:2642-2656` 一帶的動畫開關 UI、`renderer.py:1534` 的標籤區）
  加一行「界面模式：朴素 / 增強」切換。
- 與既有 `animation_enabled` / `selection_animation_enabled` 的關係：
  那兩個是「增強模式內」的細分開關；本開關是更上層的「要不要增強」總閘。
  樸素模式下本計劃所有新效果（S1–S7）一律不生效；`animation_enabled` 在樸素模式仍可獨立控制
  原有滑動動畫的有無（保持舊行為）。

**實作策略（避免複製整份 renderer）**
- 以現有 draw 函數為底，**增強層在其上疊加或切換參數**，樸素層走原本分支；

  - 純疊加層（如 S2-1 當前步光邊、S3-1 聚攏弧）：`if self.ui_mode != 'enhanced': return`
  - 替換型（如 S1-2 撤銷/重做配色、S4-1 線條參數）：`color = ENHANCED if enhanced else OLD`
- 關鍵原則：**樸素模式的代碼路徑 = 當前 master 的行為**，本分支不修改這條路徑的輸出，
  只在 `ui_mode=='enhanced'` 時插入新行為。這樣「舊版樸素 GUI」嚴格等於未套用本計劃的版本，
  也保證將來要回退時只要切到 `plain` 即可，不用 cherry-pick。

  S0-1 的「放大幅度（300ms / ±3% / 光暈）」屬增強，只在 `enhanced` 套用。

### S0-1 復原彈窗計時器根本沒被驅動 ★最高優先
**現象**：彈窗永遠停在第 0 幀——縮放 0.7、**透明度 0**、光暈 0，6 秒自動關閉也永遠不觸發。

**全項目無任何地方遞增它**（已 grep 全倉確認，只有 GUI.py:462 初始化與 1325 置零兩處寫入）。

**建議改動位置**
- `GUI.py:3531-3589 run()` 主循環：在每幀的 update 區段（`update_animation` 附近）加一行
  `if self._solved_popup_active: self._solved_popup_t += 1`
- 若要改毫秒驅動（見 S6-3），這裡改成累加 `dt_ms` 並把 `renderer.py:2220-2225` 的幀門檻換成毫秒。

**順帶放大幅度**（計時器修好後才看得出來，建議一起做）
- `renderer.py:2220-2224 draw_solved_popup`：
  - 彈入：`p = min(1.0, t/12.0)`（12 幀≈200ms、0.7→1.0）→ 拉到約 300ms、起始 0.85

**驗收**：復原後彈窗應可見且有放大過程；6 秒後自動淡出關閉。

### S1-4 縫兩端的方向標註
**前提（機制，勿再寫錯）**：縫是一把刀。選中縫後以「點擊位置所在的塊」為錨，
`game.opt(gap_type, line, block)` 選出**被縫切出來的、與該塊連通的那一整片**（`be_opted`），
再沿**與縫平行**的方向平移（`GUI.py:1525-1578`，不平行的方向會直接報「該方向與選中的縫隙不平行」）。
→ 橫縫只有左右兩個候選方向、豎縫只有上下，這條在點縫那一刻就定了；
某端到底走不走得了取決於那側有沒有空位。

**整片高亮保留不動**（原始特色）。本項只加方向標註：
- **位置**：`renderer.py` 的 `_draw_gap_direction_annotation()`，**在三形態 draw_*_board 的末尾各調一次**
- 縫的兩端各一個小圓底：能走 → 箭頭 + 可走格數；不能走 → **灰叉**
  （不用「不畫」——玩家分不清是沒畫還是不能走；也不用「灰箭頭+0」——要讀數字才知道）
- 可走格數用 `game.try_move_ex(direction, step)` 逐步試算，按 `(gap, be_opted 簽名)` 緩存，
  只在縫/切片變化時重算。
- 落點預覽**只在鼠標懸停某一端時**才畫半透明結果，常駐畫會一直飄著干擾看盤。

**幾何做法（重要，勿改成查字母表）**：
位移向量 = `game.DIRECTIONS[d]` 的**格增量** + 形態自己的 view 反算屏幕差，
即 `_key_center(key + delta) - _key_center(key)`。
→ 三角的 `'w'`（-0.5,-0.866 左上）與米字的 `'w'`（-1,0 正左）屏幕朝向**完全不同**，
任何「方向字母 → 屏幕向量」的硬編碼表必然錯其一。

**錨點 = 切片沿推行軸的投影包圍盒的「外沿中點」**，再加 `塊半徑 + 標記半徑 + 空隙` 讓位：
- 不能按整條縫/棋盤邊界算（2026-10-05 bug-b：圖層大多時間在屏幕外或被塊壓住）；
- 不能取「某個極端塊的中心」——同一投影值上常排著好幾個塊，錨點會隨遍歷順序亂跳。

**風險**：中。已由 `test/_check_gap_annot.py` 對三形態 + bug-b 驗收。

做法：正在執行的那一組滑塊加一道沿移動方向掃過的光邊（一次性，非常駐）。

### S2-2 求解狀態卡：統一容器，不統一內容
**背景**：求解中途**已有通知**（toast），但各求解器格式不一；且無法估算時長。
→ 不做進度條，做一塊**固定位置的狀態卡**：
- 第一行：狀態 + 階段名 + 一個不確定活動指示（來回掃的線 / 三點循環）
- 第二行：**已用秒數** 與 **已探節點數 / 已走步數**——這是已發生的客觀事實，不是預估
- 第三行：求解器自報指標（聚攏度、邊界盒…）原樣顯示，不強求統一

「像卡死」的解法不是進度百分比，而是**數字在動**。

**位置**：`gui/renderer.py:2144-2202 draw_macro_notify`（已有 10 幀淡入 / 30 幀淡出與
`persistent` 模式，可擴成狀態卡外殼）；
數據源在 `GUI.py:3470-3502` 一帶的求解結果輪詢與 `_pump_stream_segments`。

### S2-3 沒解出來時的收尾
現在 partial 解（如 04 這類）是**悄悄停下**的，沒有任何交代。
**位置**：求解結束分支（`GUI.py:3470` 附近的結果處理）。做法：明確的收尾提示 + 盤面灰化。
**風險**：低。注意別和競速模式的 DNF 判定打架。

### S2-4 步間「呼吸」與速度滑條拆分
連播時每步之間留 80~120ms 空檔，否則一串動作糊成一片。
**位置**：`gui/animation.py:140-142`（提交後推進下一步）；速度滑條目前只控制一個
`animation_duration`（`GUI.py:530`，範圍 50~1000ms），建議拆成「滑動時長」與「步間停頓」兩個參數。

## S5. 音效（等用戶提供素材）

用戶方案：**背景音樂 + 滑動摩擦聲 + 其他提示（復原、滑動失敗）**，
摩擦聲用**實錄的幾個魔方轉動聲 + 隨機擾動**。

### S5-1 音頻模塊與槽位
新增音頻模塊（建議 `gui/audio.py` 或獨立 `sound/` 目錄），槽位：
`bgm` / `slide`（摩擦）/ `fail`（滑動失敗）/ `solved`（復原），預留擴展。
音量分**音樂**與**音效**兩條滑條 + 總靜音，默認音量調低。

### S5-2 摩擦聲的執行細節（素材準備時就要注意）
1. **摩擦聲是持續音**，長度跟著滑動過程走（走 1 格短、走 4 格長），不是固定短音。
2. **錄音時錄長一點**（1 秒以上，帶自然衰減尾巴）。樣本若只有 150ms 而滑動有 400ms，
   硬拉伸會變調、硬循環會有接縫。短滑動截前段，長滑動輕微拉伸 + 首尾淡入淡出。
3. **隨機擾動要三路並行**：多樣本輪換（同一樣本連播三次耳朵立刻識破）、
   音高微調 ±3~5%、音量跟著滑動距離 / 速度走。
4. 建議錄**幾種不同力度**（輕推 / 正常 / 大力快速），播放時按情況挑。

### S5-3 連播節流 ★必須提前想
求解演示 30 步連播 = 30 次摩擦聲密集堆疊，會像炒豆子。
做法：演示模式下壓低摩擦聲音量，或隔幾步才出一次聲。

### S5-4 幾類音的性格分開
失敗音觸發頻繁，必須短、悶、不刺耳；復原音可以稍長，那是慶祝。

## 建議執行順序

```
S0-0（GUI 模式開關：plain/enhanced，先落地，後面每步都從這分流）
 └→ S0（修 bug：S0-1 彈窗計時器 / S0-2 面板座標 / S0-3 resize；兩模式都修）
     └→ S1（低成本高感知：事件順序 / 撤銷重做分色 / 越界回彈 / 縫方向標註 / 指針）
         └→ S2（求解演示可懂：當前步標記 / 狀態卡 / 收尾 / 步間停頓）
             ├→ S3（聚攏度弧）
             └→ S6（性能底座，與 S3 並行做，為常駐動效騰預算）
                 └→ S4（視覺統一 / 令牌化）
                     └→ S5（音效，等素材）
                         └→ S7（打磨）
```

**關於開關的兩個層級**（避免混淆）：
- `ui_mode`（S0-0）是最上層總閘：關 = 完全回到樸素 GUI（S1–S7 全不生效）。
- `減少動效`（S7）是增強模式**內部**的第二層：開 = 增強模式但只保留瞬時反饋、關掉非必要動效。
  兩者正交，可組合（樸素 / 增強全開 / 增強減動效）。

S0-0 與 S0/S1 無依賴，可以先一波做完並跑回歸；S4 的令牌化最好在動效都定案之後做，
免得改兩遍。S0-0 若定為默認 `enhanced`，則回歸時要同時驗證「切到 plain 與 master 行為一致」。
