## 2. 基線剖析（4×4×4，cProfile，22.7s）

| 熱點 | 佔比 | 說明 |
|---|---|---|
| `_box_count` 4.4M 次 | ~36% | 每次調用跑 6 個 `min`/`max` builtin |
| `cubic_metrics` 累計 | ~49% | 每個候選都算一次完整 3D 指標 |
| 候選鏈（opt / try_move_ex / restore_state / `_rebuild_blocks`） | ~40% | 每個候選 `snapshot → opt → try_move → restore`，restore 重建全部 Block |

結論與方案 §1.4 的推測一致：指標層與候選回滾鏈各佔約四成，不是單點問題。

## 3. 本輪落地（全部在 `solver/ml/cubic_gather.py`）

1. **純座標候選展開**：`cubic_candidates()` 直接用引擎 `Board.legal_moves(step)`，
   落點 = `Move.moved + step·方向 ∪ 其餘`；候選評估不再改盤面，`restore_state`
   只保留「整輪失敗回滾」一次。
   - 同時補上方案 §2.1 的唯一真缺口：**逐連通分量枚舉**，動作帶三元 `rep_cell`；
     `_apply_cubic_action` 也改為優先按 `rep_cell` 定位塊（與 GUI 回放同口徑）。
   - 連通判據仍走板型自帶的 6 鄰接 lattice，不另造 3D bitboard（避免與引擎語義分叉）。
2. **`_box_count` 去 builtin**：6 個 `min`/`max` 改成純比較夾取，語義不變。
3. **指標層省調用**：當前態指標跨輪攜帶；選中候選的指標直接作為落點指標；
   step=1 跳過逐起點的 mod 餘數判定。
4. **Φ 預篩 + top-k**（方案 P1）：`_candidate_phi` 用 O(塊數) 的兩個量
   （當前最優窗口內塊數 / 貼合候選最小角同形窗口內塊數）排序，只對前
   `phi_prescreen_k=8` 個算完整 `cubic_metrics`；`k=0` 可關閉。
5. **實心盒快速還原判定**：`_solid_goal_signature` + `_solved_fast`；
   自訂 `goal_pattern`（非實心盒）回 None，仍走引擎 48 對稱 `is_solved()`。
6. **指標補鍵**：`cubic_metrics` 增加 `holes` / `outside`（方案 §2.3 第一步）。
   `protrusion` 需要目標形狀本身，本輪不給假數據。

## 4. 實測（同一固定打亂集）

| 尺寸 | 基線 中位 / p95 | 本輪 中位 / p95 | 中位倍數 |
|---|---|---|---|
| 3×3×3 | 6.30s / 11.39s | 0.776s / 1.845s | 8.1× |
| 4×4×4 | 20.20s / 20.37s | 4.396s / 7.757s | 4.6×（基線 8 局全部撞 20s 上限，真實倍數更大） |

誠實說明：

- **解出率仍是 0/16**，基線也是 0——單次聚攏不承諾還原，這不是本輪引入的退化；
  真正要解出需接方案 P1 的逐洞/單洞收口。
- 返回步數不可跨版本直接比較：基線被 20s 上限截斷，本輪同一時間預算內能走更多步。
- 展開節點數（本輪中位）：3×3×3 6528、4×4×4 14200；候選數已從舊近似枚舉的
  ~36 漲到完整空間（4×4×4 實測 144），速度提升是在**動作空間變大**的前提下取得的。
