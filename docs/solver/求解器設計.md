# 求解器設計（總覽與速查）

> 面向「以后继续更新时快速参考」的设计总账。记录**现状**、**为什么这么设计**、**踩过的坑**。  
> 词汇遵循《術語規定》：**空位 = 缺口＋孔洞的统称**；窗口内空格叫**洞**，窗口外多出的方块叫**凸起**；「聚拢度」= 最佳窗口覆盖的方块数（复原 = 满值 m×n）。  
> 验收口径（也就是重要性，2026-09-30 拍板）：**运算时间 > 解的长度**。所有对比实验以时间短为主指标，步数少只作副指标，如果兼顾二者的情况下，还可以考虑可解读性（以人类的视角理解每一步的逻辑）。

## 1. 地基：动作与引擎语义（solver 的一切建立在它上面）

- 引擎 `game.py`：`opt(缝类型, 缝线, 块)` 把**该缝一侧的连通分量**整体选中 → `try_move(方向, step)` 验证滑动（**全盘级连通性检查**：分量滑远会断连）→ `commit_move` 提交。
- 动作 5 元组：`(gap_type 'h'/'v', gap_line, side, move_dir, rep_cell)`。前 4 位与游戏原生语义一致；**第 5 位 rep_cell = 分量中任一格**，用来消除「同缝同侧多分量」歧义（`apply_action` 恒取首个分量的老缺陷靠它绕过，见 §8）。
- 位移距离：引擎一次只滑 `step` 格；存档/规划里 dist∈1..8 的动作要**拆成 ceil(dist/step) 次连滑**，rep 逐步平移，否则重放走样（07 教训）。
- `is_solved`：任意位置的 m×n 或 n×m 实心满方阵即复原，不看坐标、不看编号。

## 2. 核心概念词典

| 概念        | 定义                                                          | 代码锚点                                                            |
| --------- | ----------------------------------------------------------- | --------------------------------------------------------------- |
| 窗口        | 包含最多方块的 m×n/n×m 矩形区域（= 目标区域）                                | `fill_macro::window_of`                                         |
| 洞 / 凸起    | 窗口内空格 / 窗口外方块（凸起＋空位才可能配对）                                   | 同上                                                              |
| mod 配对    | 洞 h 与凸起 p 必须满足 `(p-h) % step == 0`（行、列各自）才可能配对——滑动的守恒律      | 轮询层 tasks 过滤                                                    |
| 聚拢度       | 最佳窗口覆盖方块数；**所有产物的验收闸门**：只接受「回放后聚拢度提升」的动作序列                  | `gather_solver::find_best_window`、`fill_macro::_overlap_raised` |
| 完美洞       | 8 邻全是方块（无缺口）的洞；标准切割对完美洞必有效，对不完美洞可能无效                        | `fill_macro::hole_gaps`                                         |

## 3. 查表求解器（有表尺寸的最终答案）

`solver/table_solver.py`，数据 `solver/data/{m}_{n}_{step}/table.pkl`（.gitignore，不入库）。

- 预建 BFS 距离表（`build_table.py`），求解 = 从当前状态沿 dist-1 邻居走回目标，重构最短动作序列。
- **保证最优、亚秒级**。有表的尺寸没有理由用别的（`hybrid_solve_with_table` 在入口强制先查表）。
- 新尺寸建表成本指数涨，大尺寸走不起 → 这就是「免表兜底」存在的原因。
- 配套 CLI：`table_query.py`（status/dist/solve/verify）。

## 4. 混合求解器 hybrid（无表兜底·非最优）

`solver/hybrid_solver.py`，入口 `hybrid_solve_with_table`（= 查表失败才走 `hybrid_solve`）。

- 流水线 `pipeline='alt'`（默认）：多段「**聚拢 alt_chunk 步 + 填洞宏**」交替，直到无法改进 → 逐次单缺口 GBFS 消解。exp20 实测比旧流水线快约 4.5 倍。
- `pipeline='legacy'`（回退）：全程梯度聚拢 → 填洞宏 → GBFS。
- 每段动作带 rep_cell、以「从初始态重放」锚定坐标系，最终输出与查表一致，GUI 可直接播放。
- 定位实话：解长中位是最优的 17 倍级。它是**能出解**的保底，不是好解。

**时间剖面（重要结论，勿推翻）**：聚拢约 30 ms/步、搜索约 1200 ms/步，差 40 倍。聚拢的作用不是缩短解，而是**用廉价的步数换掉昂贵的搜索**。砍聚拢换搜索 = 时间暴涨（实测 +70%）。

## 5. 宏求解器主线（当前主力）

### 5.1 总入口 `solve_gap_macro`（solver/ml/gap_solver.py）

按局面判型分发：

1. **单洞 + 边缘缺口（L/R/U/D/CORNER）** → `solve_gap_any`：**双层共轭**。  
   公式 = `A [Setup] B C B′ A′`：A = 外层封壳（把缺口上方堵住，缺口变封闭孔洞＋清出通道），C = 单格跳进洞，B-C-B′ = 对人造孔洞跑填洞宏（只取目标洞那段，不整算法调用——它会矫枉过正）。回退路径 = 甩料＋垫洞。  
   缺口旋转归一化到上边缘再套公式（`view_rotate` 处理刚体旋转，把「凸起在任意侧」统一转到右侧）。
2. **多空位（洞+缺口混合）** → `solve_multi_vacancy(mode='auto')`：统一贪心驱动，洞走填洞宏、缺口走补缺链，验收同一把聚拢度闸门。
3. **单洞封闭孔洞** → `solve_fill_macro` → `solve_single_void`。

流式协议：`segment_cb` 每解决一个 couple 回调一次，GUI 边算边播；返回协议含 `fill_stream / fill_partial / fill_fail` dict。

### 5.2 填洞宏 `solve_single_void`（单洞原子）

- 不带 couple：单洞单凸局面整盘求解；带 `(hole, anchor)`：只产出「把该凸起填进该洞」的动作段（可能 partial），是否采纳由调用方按闸门验收。
- 结构 = A-B-A′ 共轭子宏（Setup 可选：孔洞与凸起同排时先挪开凸起）。
- 视图旋转归一化：先把凸起转到窗口右侧再套固定骨架，产物逆旋转回世界坐标。

### 5.3 轮询层 `solve_multi_void`（多空位贪心驱动——**理解求解器的核心**）

用户 2026-10-01 的设计思想：像解一堆有隐含依赖的问题——**不能预先知道哪个要先解，就一直轮询，谁有成果就收谁，失败无副作用换组**。每轮尝试顺序：

1. **普通 couple**：枚举全部 (洞, 同mod凸起)，并行（可选）或串行逐对喂给 couple 求解器。产物过聚拢度闸门才推进活盘。**partial 也算成果**（有提升就收）。
2. **贴边缺口 setup `_edge_setup_chain`**（2026-10-02，06 修复）：缺口方向在窗外时，补缺链必产出灾难方案（封壳逆操作会把整组抬出窗外）。用户手解归纳的通则 = **先用一次整体平移把窗外那侧空区填上块**（等效窗口外扩一圈），缺口变普通洞，老算法接手。  
   实现 = 往返捎带六段骨架 `T1→T2→T_last→P→C→R`：推带腾通道（T1 垂直推出、T2 横移对齐造锚——引擎全盘连通性检查要求）→ 带行块推向源侧（T_last）→ 窗外源块就位（P）→ 回程捎进洞（C = T_last 逆）→ 逆序还原（R）。枚举方向×侧×距离，单洞预算 6s。
3. **带移让位＋粘上接走 `_band_shift_chain`**（2026-10-02，07 修复）：三段——
   - **洞带让位**：含洞邻块的整带沿缝法线平移 k×step，洞被挤到带外缘。**幽灵块在此段追踪洞身份漂移**（07：(7,2)→(9,2)，从 1 数 = 第 8 行第 3 列 → 第 10 行第 3 列）。只此段在幽灵盘上跑，随后撤幽灵。
   - **源接应**：模式 A（源已粘连 → 直接平移）；模式 B（**粘上接走**真义：邻近分量**反向**平移贴上源块，再**正向**平移带回——不是「源块所在带直接平移」，让位后全盘连通，opt 会选中大分量，07 实测撞过）。
   - **带回位**：把源块捎进原洞。  
     判据 = 原洞位被真块占据 + 真盘整链重放合法 + 聚拢度闸门。07 实测：6 步 0.07s（与用户手解步数一致）。
4. **中性整形预演 `_shaping_progress`**：couple 宏的最小原子是完整 A-B-A′，有些卡点要先花 0 增益的整带步「揉形」才肯动。这里做 ≤2 步不降聚拢度的 BFS，终点只要聚拢度提升或解锁了新 couple 就收。
5. **停机诊断**：全败时报告完美洞/不完美洞数量（8 邻有缺口 = 不完美洞，标准切割必败）。

贪心未全解 → **宏级 DFS 兜底 `solve_multi_search`**（见 §5.4）。

**并行轮询**（2026-10-01 用户思想，已落地默认关）：`_run_couples_parallel`，环境变量 `GATENNEA_PARALLEL=1` 打开。实测轮询层单次尝试毫秒~秒级，进程池 spawn(~5s)+序列化是负收益；**真正值得并行的是 DFS 整形边**（convoy 53s/次、粘补 15s/次），基础设施已就位待接入。

### 5.4 宏级 DFS `solve_multi_search`（回溯兜底）

- 动机：贪心存在顺序依赖——同一盘面换个候选随机序，一个能全解一个停机（失败05/08/09 实证）。解存在但贪心选错 → 对 couple 选择做 DFS 回溯。
- 状态图：节点 = 盘面，边 = 一次「hook 成功且闸门通过」的 couple。每条边窗口方块数严格 +1 → 深度有界、无环；同中间态去重。
- **整形边**（惰性探测：couple 有戏就不花整形探测的钱）：刚体填入 `_rigid_fill`（与 convoy 同构的刚体平移版）、粘上接走 `_convoy_fill`、带移等。共享预算 `convoy_left=8000`、`paste_left=2`。
- **总时间预算 `_SEARCH_TIME_BUDGET = 60s`**（2026-10-02 用户拍板「算不出来尽早发现，发现就停」）：dfs 入口/couple 循环/整形边三处检查，到点立即停机报告。实测死局 04: 215s→91s、07: 215s→121s（后者修通后归零）。

### 5.5 移形换位救援 `_compact_rescue` / `_swap_fill`

紧凑盘（m、n ≤ 2×step）专用最后手段：常规链全败后，**step 级组移动作的全量双向 BFS**（正向从当前局面、反向从全部还原态，中间相遇）。用户「2×2 整组互换位置机动」的教学参数化。BFS 最短性保证不劣于手解。

### 5.6 手动单段 `solve_single_segment`（GUI Ctrl+G）

用户逐段点名驱动：点选窗外凸起（可选先点一个空位指定配对，否则自动最近同 mod）→ 求解链 = 缺口→补缺链；CORNER→角链；孔洞→填洞宏 couple；全败→convoy 兜底。成功标准只要求**目标洞被填**，不要求整盘还原——驱动权在用户手里。

## 6. ML 线（现状：搁置，方向保留）

- **训练线数据源从来是存档直读 + BFS 表**，与标注模式无关（标注模式 2026-10-02 转型为「AI 分析存档 + 标注辅助」，见 §9）。
- **距离拟合已被本轮实现证伪**（注意：是**实现**没学到信号，不是用户提出的方向没价值）：
  - exp18：5_5_2 真值分布退化（75.5% 全是 dist=4），「永远猜常数 4」比训练出的模型还好——之前的好成绩是分布幻觉。
  - exp17 四路对照：同骨架只换打分，oracle（真值距离）0.11s 还原 vs 现有 400 步——**贪心骨架极强，全部瓶颈在打分函数**。
  - exp19：贪心对随机噪声极宽容，对系统性偏差（同类局面稳定估错）致命。
  - **重启的最低验收线**：4_4_2（真实距离跨度 0~17）上显著优于「猜常数 9」（MAE 1.282 / ±1 65.3%）。达标前不要再投 HistGB 调参时间。
- 备选方向：深度受限前向搜索、真正的下界估计、组合不变量。

## 8. 已知死局、盲区与未修缺陷

1. **段级聚拢度闸门盲区**：闸门只认「窗口方块数提升」，对两类真推进会误拒——①洞数减少但窗口漂移（聚拢度持平）②方阵整体搬运途中填洞（持平）。候选辅助判据：洞数计数/满方阵达成检测。**提出待拍板**。
2. **方阵搬运（07 深层课题，等用户定方向）**：07 手解的本质是把整个方阵从 rows 1-8 整体搬到 rows 3-10，填洞只是副产品。带移让位链只解决了单洞卡点；「以什么为目标导向规划整体搬运」仍是开放问题。
3. **04**：partial 76.8s 收尾，剩两个不完美洞。已排期暂缓（用户：先不研究）。
4. **`apply_action` 多分量歧义（未修）**：动作 4 元组不含分量信息，同 (缝,侧) 多分量时恒取首个。所有现役求解器靠 rep_cell（第 5 元）绕过，未根治。正确修法 = 全线 5 元组化，但牵动存档回放/宏录制兼容性，需单独排期（详见 `../math/核心玩法形式化.md` §2.6）。
5. **闸门灾难方案回顾**：补缺链对贴边缺口会产出「填上缺口但 30 块搬出窗外」的灾难——闸门正确拒了它，但意味着**每类新机构都要配「段级真盘重放 + 闸门终裁」**，不要信任机构内部局部判定。

## 9. 周边设施

- **存档解码**：`test/decode_frames.py` 帧间暴力解码（枚举缝×线×侧×分量×方向×距离1-8），`decode_pair` 为单帧对照原语。存档的 history.snapshots 就是手解全过程（最后一张 = 复原态；**中间快照才是失败局面**）。重要研究/教学档已入库到 `archives/*.json`（失败01~09、教学实例等，2026-10-02 自 save/ 迁入）；`save/` 是玩家实时存档目录，不入库。
- **标注模式**（`gui/annotation.py`，B/Z/M/S 隐藏入口）：2026-10-02 转型为「AI 分析存档 + 标注辅助」。幽灵滑块重写了空位追踪（洞随带漂移不再误判「被填即完成」）；帧差解码对照（`decode_move_candidates`）每步比对真实动作，`decode_alt/decode_ok` 随 JSONL 写盘（歧义步 AI 重点核）；阶段 phase 支持自定义名（「粘上接走」「移形换位」等）= AI 语义分段标签。

- **回归** `experiments/_regression.py`：22 案标准回归（含 22 个真实死局/教学存档），任何求解器改动必须跑，零退化才准推。
