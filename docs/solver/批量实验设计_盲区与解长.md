# 批量实验设计：求解器盲区覆盖 + 解长质量（一趟收集）

> **受众**：AI / 開發者
>
> 回答两个问题：①「两层都失败」的局有多少、长什么样（豆包 §5 的前置验证）；②能解的局，解长离最短差多少（上帝之数标尺）。
> 依据：`docs/solver/求解器AI搜索优化方向.md`（量差距）+ `docs/豆包文档/转交文档_API改进与求解器AI结合.md` §5（失败样本聚类）。

## 1. 数据源（全部复用，不新造）

| 源 | 工具 | 性质 |
|---|---|---|
| 随机盘面 | `experiments/harness.py` 的 `gen_state`/`build_corpus` | 正向随机游走生成，**必然可解**，seed 可复现 |
| 玩家存档 | `save/*.json` 回放 history 得盘面 | history 中段局面**不保证可解**（玩家可能走进死局）——这正是真实失败样本来源，单独标注 `src=save_mid` |

- 尺寸选择：**(4,4,2)**（上帝之数 17、9 死局有黑名单可判）、**(4,4,3)**（29、6 死局）、**(5,5,1)/(5,5,2)**（无数学真值，量覆盖度）、存档局按尺寸分布挑（4×4~8×8 都有存量）。
- 豆包的 `solver/ml/data/human/human_samples.jsonl`（5033 动作/87 局）**仓库里不存在**，本实验不依赖，改为自建可复现语料。

## 2. 每局量什么（判定口径）

入口 `auto_solve(game, step, stage_cb=rec, time_budget=180)`，按返回协议分拣：

| 结局 | 判定 | 记录字段 |
|---|---|---|
| 全解 | 返回 `(actions, reps)` tuple | 解出层（stage_cb 最后 solved 段 label：①查表 / 补缺宏 / 混合流水线 / 续算）、总步数、总耗时、各段耗时 |
| **失败·有部分成果** | `{'type':'fill_partial'}` | **动作链回放存失败样本存档（§3）** + 终态 score/phi + 耗时 |
| 失败·零提升 | `{'type':'fill_fail'}` | 停在初始态（= 历史最优即初始），存双快照存档（§3） + 耗时 |
| 异常/取消 | `False` / raise | 完整 traceback |

> 依据（用户 2026-10-15 确认「本来就是这样的」）：`auto_solve` 全败时若 `best` 有聚拢度提升即返回 `fill_partial`（动作链 = 到历史最优态的全过程）；`best` 为空（连初始态都没提升）才 `fill_fail` 零动作——此时初始态即历史最优，停原地语义成立。`best` 择优只比聚拢度，「并列取 Φ 最小」裁判在 GUI 层（stage_cb checkpoint），求解器内部未做。

- 疑似死局标注：`solver.deadend_guard` 黑名单命中 → `deadend: true/false/unknown`（当前仅 (4,4,2) 有 9 局真值，其余尺寸 `unknown`）。
- time_budget 180s/局硬顶（auto_solve 内部续算已有 90s 上限，再套一层防极端局拖死；超时也计入失败并标 `timeout`）。

## 3. 失败样本 = 标准游戏存档（用户 2026-10-15 拍板改）

失败样本不存私有 JSON，直接存成**游戏标准存档**，可在游戏里 `Ctrl+O` 打开复盘（或经成绩记录「载入练习模式」载入）。

- **目录**：`save/blindspot/`（`save/` 整体在 .gitignore，属用户数据约定，零 git 污染）
- **文件名**：`blindspot-<step>-<m>-<n>-<seed>.json`，如 `blindspot-2-4-4-1007.json`
- **存档结构**（与真存档同构，`gui/file_ops.py` 的 data 协议）：
  - `version=1`、`puzzle={m,n,step}`（方形）、`checksum` 按 `_compute_checksum` 同算法（puzzle+history 序列化 SHA256，排除 checksum 自身）；
  - 快照由 `history.GameHistory.save_snapshot(game)` 生成，字段 100% 兼容 load 路径。

### 3.1 失败·有部分成果（fill_partial）——主场景

求解器失败时停在历史聚拢度最大的那一刻（`auto_solve` 的 `best`，返回完整动作链）。存档 = **完整回放这条链**：

- `snapshots = [复原态] + [逐步回放动作链，每步一快照]`（`apply_action` 逐步 apply，同 `_end_state` 的 5 元组回放口径）；
- `history_index = 最后一帧`（停在最优终态）、`step_count = len(actions)`；
- 打开存档看到的就是「求解器尽力达到的最好局面」，undo/redo 可回看它的完整尝试过程——**历史全部在档**。

### 3.2 失败·零提升（fill_fail）

连初始态都没提升（best 为空）——初始态即历史最优，停原地：

- `snapshots = [复原态, 初始盘面]`，`history_index=1`，`step_count=0`（= 「刚打乱完、求解器零进展」）。

### 3.3 元数据分离

元数据不进存档（会破坏 checksum 语义/load 只认固定字段）：`outcome`（partial/fail）、`score`、`phi`、`deadend`、`stages`、`total_s`、`src`、`seed`、**对应存档文件名**全部记入 `rounds.jsonl`，用文件名关联。

用途：① 游戏内人工复盘「连求解器也解不了」的局（从它停下的最好处继续尝试，而非从零开始）；② 事后按凸起/缺口/包围盒/连通结构/Φ 分组的素材（从存档 matrix 直接解析，终态快照即失败盘面）。

## 4. 执行策略（绕本机 10~15 分钟后台截断）

- 分块：每块 6~8 局独立进程跑，脚本 `--start/--count` 参数化；
- 每局结果立即追加 `results/blindspot/rounds.jsonl`（一行一局，JSONL）；
- 断点续跑：启动时读已有 seed 集合，跳过已跑；
- 一律 `-u` 无缓冲 + 实时落盘（防 stdout 黑洞 / 管道截断）。

## 5. 规模与耗时预估

- 单局成本：4×4 秒级~十几秒；5×5 分钟级；6×6 以上及深局 2~5 分钟（兜底搜索 1204ms/步 × 几十步）。
- **冒烟档**（先跑）：(4,4,2)×15 + (4,4,3)×10 + (5,5,1)×6 + (5,5,2)×6 ≈ 37 局 ≈ **30~50 分钟**。目的：验证分拣口径、落盘、分块衔接，同时出第一份粗分布。
- **正式档**（冒烟通过后）：(4,4,2)×60 + (4,4,3)×40 + (5,5,1)/(5,5,2)×各 40 + 存档中盘 30 局 ≈ 210 局 ≈ **2.5~4 小时**。口径与冒烟完全一致，数据合并分析。

## 6. 输出物

**入库（随实验结论提交）**：
1. `results/blindspot/汇总.md`：各尺寸成功率 / 失败率 / 分层成功率（哪层解的）/ 解长分布 / 耗时分布；
2. (4,4,2)/(4,4,3) 的**解长 vs 上帝之数（17/29）差距表**——「量差距」的标尺数据；
3. 初步分组报告：失败样本按凸起/缺口/Φ 的分布（聚类的第一刀，回答豆包的「集中少数类 / 五花八门 / 极少」三岔口）。

**不入库（过程产物/用户数据）**：
- `results/blindspot/rounds.jsonl`（逐局原始记录）；
- `save/blindspot/*.json`（失败样本存档，游戏内复盘用，随用户机器留存）。

## 7. 风险与对策

| 风险 | 对策 |
|---|---|
| 后台长任务被外部杀（exit=127，实测 10~15min 天花板） | 分块 + 每局落盘 + 断点续跑 |
| 真死局 vs 能力盲区混淆 | 黑名单标注 + 语料局（必然可解）与存档中盘局（可能死局）分列统计 |
| 大尺寸/深局过慢 | time_budget 硬顶，超时计入失败并单列 |
| 单局结果差异 | seed 固定可复现；不追求逐局稳定，看分布 |
