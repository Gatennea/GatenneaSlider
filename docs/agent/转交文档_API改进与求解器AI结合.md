# 第一部分：API 改进（可立即落实）

优先级：🔴 严重（卡死/误导）｜🟡 中（体验/效率）｜🟢 轻。

### 🔴 A1. 命令异步化改造包（原 A1+A8 归组：同步阻塞 + 无取消通道）
- **现象**：`/shuffle` 首次超时返回"命令处理超时"但命令仍在后台跑；GUI 主线程忙时所有请求（含 `/status`）排队阻塞 → 服务假死；无"忙"状态；卡死命令无取消手段。
- **根因**：GUI 主线程串行消费 `cmd_queue`；HTTP 层 `resp_q.get(timeout=30)` 等结果，超时即报错但不取消；`/quit` 也被同一主线程阻塞。
- **改动（一套改造，勿拆两半实现）**：
  1. 长命令（shuffle/求解/大棋盘动作）改**子线程或子进程**执行，GUI 主线程永不阻塞；
  2. 命令执行中返回 `202 + task_id`，提供 `/tasks/<id>` 轮询进度/结果；
  3. 命令带 `cancel_token`，提供 `/commands/<id>/cancel`；
  4. HTTP 与 GUI 主线程解耦（独立线程池），保证"控制面"永远可响应；
  5. 至少 `/status` 加 `busy: bool` + `current_command` 字段。
  - ⚠️ 实现取舍需明确：pygame 渲染必须在主线程，**子线程执行长命令时不得触碰 pygame 状态**；若改造困难，优先"独立进程"方案（见 A2），避免半吊子线程改造。
- **验收**：发起慢命令后 `/status` 立即响应且 `busy=true`；命令期间其它请求不阻塞；卡死命令可被取消，取消后 HTTP 仍可响应；超时文案明确"命令可能仍在执行，请轮询 /status"。

### 🔴 A2. 重型依赖懒加载 → GUI 主循环死锁
- **现象**：`shuffle` 首次触发 `import numpy`（经 solver 链路）→ numpy 扩展在 SDL 主线程首次加载 → DLL 死锁，窗口 Responding=False。
- **现状**：`main.py` 顶部预热已缓解 shuffle 路径；但**其它未预热路径（求解器全家桶）仍可能踩**。
- **改动**：
  1. 首选：把求解/打乱放**独立进程**（多进程隔离，顺带解决 A1）；
  2. 次选：启动时统一前置 import 全部重型模块——**注意权衡**：会拉长冷启动时间（numpy+求解器全家桶），需实测启动耗时可接受度；
  3. 至少给 http_server 加"看门狗"：主线程长时间无响应时 dump 栈/重启。
- **验收**：干净环境冷启动后，首次 shuffle、首次 solve、首次 /analysis/actions 均不卡死。

### 🟡 A3. JSON body 不兼容 UTF-8 BOM
- **改动**：http_server 读 body 用 `encoding='utf-8-sig'` 或 `body.lstrip('\ufeff')`。
- **验收**：带 BOM 的 JSON body 请求成功。

### 🟡 A4. 鉴权令牌的获取与启动竞态
- **改动**：
  1. 服务未就绪返回 `503 Service Unavailable`（而非 401 令牌无效）；
  2. 令牌支持固定/持久化选项，或提供 `--auth-off` 本机调试开关（注意：该开关只应绑定 localhost，勿全局关闭鉴权）；
  3. 错误区分 `token_missing`/`token_invalid`/`service_busy`。
- **验收**：进程刚起、HTTP 已监听但 GUI 未就绪时，请求返回 503 而非 401。

### 🟡 A5. shuffle 参数写死、外部不可控
- **改动**：`/shuffle` 支持 body `{bias, min_score, attempts}`（带默认值），响应回显实际参数。
- **验收**：外部可控制打乱难度；不传参数时行为与现状一致。

### 🟡 A6. 动作分析：preview 单步、actions O(N²)
- **改动**：`/analysis/preview` 支持 `steps` 或多步预览；`/analysis/actions` 支持按缝隙/方向过滤或增量枚举（实现方式：按缝隙/方向参数裁剪候选，或增量缓存，勿盲目全量重算）。
- **验收**：10×10+ 大棋盘 actions 延迟明显下降；preview 能看多步后终态。

### 🟡 A7. 错误信息不友好、无错误码分层
- **改动**：统一响应体 `{ok, error_code, message}`，error_code 用稳定枚举（`invalid_param`/`unauthorized`/`busy`/`timeout`/`command_running`…）。
- **验收**：调用方可程序化区分参数错/权限错/服务忙/执行中。

### 🟢 A8. API 文档与状态机说明不全
- **改动**：补 `/timer/*` 参数表、timed 模式 `timer_state` 状态机（idle→ready→running→finished）、`/mode` 副作用、undo/redo 边界。
- **验收**：`/help` 下各端点语义无需读源码即可理解。

### 🟢 A9. 进程生命周期脆弱、状态恢复语义不透明
- **改动**：`/status` 加 `restored: bool` + `restore_note`；提供显式 `/new_puzzle` 端点。
- **验收**：外部程序能区分"恢复自临时存档的完成态"与"新局"，能干净开局。

### 值得保留（勿改坏）
- stdin 不设防、HTTP 必须鉴权；Bearer 头 + URL 参数双通道；写操作统一 select_gap→select_block→move 三步序列；undo/redo 无参数 + /analysis/actions 可"有底试错"。
- 提示：API 层若能提供 `animation: false` 加速模式，会更适合程序控制（对 AI 高频调用影响大）。

# 第二部分：求解器 + AI 结合方向（研究，非可立即落实）

> 目标：在"当前最优却不保证求解"的基础上，找到 AI 真正能补的位置。**先验证假设，再谈方案。**
> v2 重审修正：**否决"AI 在线仲裁/介入时机"路线**（理由见 §4），改为"AI 离线公式挖掘器"定位。

## 1. 现状认知（求解器真实架构）
- 混合求解器 = **公式层 + 兜底层**，与人类求解同构：
  - 公式层（两阶段）：前段"聚拢"（看大致形状判断怎样更接近正方形 → 梯度聚拢）；后段"填洞"（决策"哪个凸起→哪个空位" → 补缺宏/填洞宏 `fill_macro`/`gap_macro`）。
  - 兜底层：因"凸起→空位"组合**无法穷举**，公式生成器只覆盖一部分，覆盖不到掉到 GBFS/fill_partial 搜索兜底。
- 结论：**"最优"来自公式库覆盖常见结构；"不保证"来自兜底搜索也非万能**（深死局、公式盲区）。
- 历史事实：**"训练 AI 求解器"方向作者已正式放弃**（readme_to_agent §4.2/§12）；`human_solver`（打分+贪心）未接入求解菜单。

## 2. 人类存档分析结论（5033 个动作，87 局完成）
- 方向**完全均匀**（a/d/s/w ≈ 各 25%），无方向偏好 → 人类每步随盘面结构现算。
- 动作峰值在**聚拢段 void 7-12（41%）**，收尾 void 1-2 仅 4.5%。
- **注意（v2 修正）**：人类解法本质是**公式化两阶段**（聚拢公式 + 填洞公式），不是"聚拢贪心"。动作序列上看不出宏，**因为宏是"条件→规则"的生成公式，条件不同则输出序列不同**——从分布统计宏是无效方法。
- 与 `gather_solver`/`human_solver` 同构：人类/公式都是"聚拢度驱动 + 局部公式判断"。

## 3. AI 结合的核心定位：离线公式挖掘器（v2 重定位）
> 一句话：**AI 不参与在线求解，只做离线"从失败中总结新技巧"，扩公式库。**

闭环：
1. 求解器（公式+兜底）跑批量存档/随机盘面；
2. **兜底失败的样本 = 公式盲区**（当前最稀缺、最有价值的信号）；
3. AI（或规则聚类）从失败样本中归纳**"可公式化的新类别"**——即"这类凸起→空位组合能用一个生成规则统一处理"；
4. 新类别编码成宏，塞进 `fill_macro`/`gap_macro`；
5. 公式库扩大 → 兜底依赖减少 → 回到 1。

**为什么这个定位站得住**：
- 与人类学习同构（先失败→总结技巧→技巧进库，如 `手解技巧备忘.md`）；
- 不需要 AI 实时判断（避开在线可靠性/幻觉问题）；
- 不改变"无法穷举"的数学本质，但**逐步扩大覆盖**，方向可收敛；
- 完全复用现有宏架构，失败样本是现成的（存档 + 求解器可批量生成）。

## 4. 已否决的路线（勿浪费算力）
- **❌ AI 在线仲裁"公式 vs 盲区"**：公式库能否处理当前局面是**确定性可检测**的（遍历宏库匹配）→ 需要的是代码检测器而非 AI；若盲区不可判定，AI 判断同样不可靠。两头不成立。
- **❌ AI 现场为单盘面生成一次性公式**：本质仍是"生成公式"，上限受"能否可靠生成"限制——即"训练推理模型没效果"的同一堵墙，只是换到运行时。
- **❌ 重新训练 human_solver 类模型**：作者已放弃；打分+贪心架构缺长程，数据（5033 正样本）也不足以覆盖。

## 5. 建议的最小验证实验（先做，再决定是否上 AI）
**目标**：确认"公式盲区是否可聚类成有限类别"——这是"公式挖掘器"路线成立的前提。
1. 用 87 局存档 + 求解器，跑批量盘面，收集**兜底失败的样本**；
2. 对失败样本做**形态聚类**（按：凸起位置/空位分布/包围盒/连通结构）；
3. 统计聚类结果：
   - 若失败集中在**少数可枚举类别** → 直接扩公式库（人工/AI 编码新宏），**不需要 AI 挖掘**，收益最大；
   - 若失败**形态分散、类别不可枚举** → 才进入"AI 公式挖掘器"路线（AI 从每簇提炼生成规则）；
   - 若失败样本本身极少 → 求解器已足够，此方向整个搁置。
4. 产出："公式盲区形态分布报告"（类别数、每类样本数、可公式化判定依据）。

## 6. 给落实 AI 的明确指令
- **不要**重构求解器核心，不要接入 human_solver，不要训练新模型，不要做在线仲裁。
- **先**执行 §5 的最小验证实验，产出"公式盲区形态分布报告"。
- 据报告三分支决策（扩公式库 / 上 AI 挖掘 / 搁置），再回来讨论下一步。
- 参考资产：`solver/ml/data/human/human_samples.jsonl`（导出产物）、`docs/` 下求解器与数学文档、`experiments/` 下既有验证脚本。
