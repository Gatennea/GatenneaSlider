## 六、⚠️ 像素断言有三条坑（2026-10-29 一次踩到，别再踩）

「画面上有没有这个东西」看起来可以直接数像素，实际三步都能给出假结果：

1. **隔点采样会猜奇偶**：目标框是 **1px 宽的线**，`range(0, h, 2)` 只数偶数坐标；
   而窗口宽度跟着 `config/config.json` 里记的上次尺寸走（本机存的是 1003，默认
   1000），差 3px 就足以让整条竖线落到奇数 x → **一个数都数不到**，报「框没画
   出来」，而框其实画得好好的（逐点取色就是 (80,220,100)）。
   → 凡是判「有没有细线 / 细字」，一律**全像素扫描**（`pygame.image.tobytes`）。
2. **数「纯黑」证不了画了字**：SimHei 小张号（12px）走 `render(antialias=True)`
   时**没有任何像素的 alpha 到 255**（实测最大 234），blit 到任何底色上都只会被
   混成「很深的灰」而不是精确的 (0,0,0)。而且「全透明背景像素」的 RGB 恰好也是
   (0,0,0) —— 数出来的 168 里有 110 个是字表面的透明背景。
   → 要证「多画了东西」，就**拿同一份几何、不给内容画一遍当基线**，逐像素比差异。
3. **判「塞不塞得下」要用 `font.size()`，不能用 `render().get_size()`**：后者
   是**含行距留白的表面尺寸** —— SimHei 8px 的表面高 11px，字本身只有 8px。
   8×8 打乱态每块 12.6px，用表面尺寸判就是 `11 > 12.6×0.7` → **64 块全被跳过**，
   缩图上一个数字都没有，而且**没有任何报错**（静静地什么都不画）。

另有一桩连带：**本机 `config/config.json` 存的窗口尺寸会让一批「截图/像素」类
测试与干净环境结论不同**。看到这类红，先把它带上跑一遍干净 HEAD 的工作树再下
结论（`git worktree add <dir> HEAD --detach`，把本机 `config/config.json` 拷过去
复现），别急着当成回归。

## 七、⚠️ 拿提示文案判状态时，别用子串匹配数字（2026-10-29 踩到，已修）

`shuffle_puzzle()` 的提示是 `已打乱：40步（练习模式）`。护栏
`_test_model_legacy_save` 原先用子串判「有没有走」：

```python
check('0步' not in good_msg, ...)   # 「好盘应该走得动」
```

**这是错的**：`'已打乱：40步'` 里当然也含 `'0步'`。而打乱步数每次都不一样
（同一份存档连跑三次实测 40 / 50 / 61）→ 只要尾数是 0（10/20/40/50/60…）就
**假红**，约 10% 的复现率，而且看起来像「存档坏了」，非常误导。

→ 判「走了几步」就把数字取出来比：`re.search(r'已打乱：(\d+)步', msg)`。
同类写法（`'没有' in msg`、`'0' not in init_map`）里，**只有涉及数字的那几条
危险**——固定词（'凸起' / '晶格' / '滑不动'）做子串匹配是安全的，别一刀切。

顺带一条：**测试里摸 `gui.game.board` 之前先确认是模型板**。引擎层只在模型
板上挂 `board` / `spec`，内置档位（square / triangle / mi）是 `SliderMatrix`
之类的老对象，没有 `board` 属性 → `AttributeError`。跨档位巡检要按形态分派。

## 八、⚠️ 测撤销/重做时，会「假绿」的三条（2026-10-30 一次全踩到）

`undo()` / `redo()` 有好几条分支，**不是每次调用都真的还原盘面**。写护栏时少
注意一条，测试就会全绿而什么都没验：

1. **动画必须关**（最坑）：`gui.undo()` 在 `animation_enabled and
   animation_duration > 0` 时走 `_start_undo_redo_animation` 分支 —— 只调了
   `peek_undo()` 就返回，**根本不还原**。而 `peek_undo()` 有副作用：它会把
   合并段惰性展开、`history_index` 跳到段末。于是「index 变了、盘面没动」，
   断言看起来还都成立。→ 测试里一律
   `gui.animation_enabled = False; gui.animation_duration = 0`，并**额外断言
   「真的走过了 N 步」**（`_test_groups_save` 的 G11c）防止它悄悄退化。
2. **别用 `restore_snapshot(g, i)` 直接跳来代替 `undo()`**：直接跳**不走**
   `_ensure_step_granularity`（合并段惰性拆分），而玩家按 Ctrl+Z 走的正是
   这条路 —— 两者是**不同的代码路径**。2026-10-30 抓到的「拆出的中间态丢
   捆绑」就只存在于后者，G10c 那种跳法永远验不到。
3. **`move_info['moved_positions']` 必须是「移动前」的真实坐标，且不能为空**：
   ① `b.location` 是可变对象、`commit_move` 原地改写 → 必须在 commit **之前**
   采集；② 传空列表会让 `expand_snapshot_moves` 走「不展开」的兜底，
   合并路径直接被绕开（我第一版巡检就是这样，白跑）。

**怎么判断一条撤销护栏有没有变空**：把它针对的修复**临时撤掉**再跑一次，
必须变红。G11 就是这样验的（撤掉 `'groups'` 拷贝 → 红，恢复 → 绿）。

## 十五、⚠️ 为跳过一条已知红而 `--ignore` 整个测试文件 = 把同文件护栏全雪藏

## 二十二、⚠️ 設置頁「最大等待秒數」曾經是「每個求解器各等一次」（2026-11-09）

離屏探針（當日一次性腳本、未入庫）實測：
`auto_solve(stage_budget=3)` 在 6×6 / 7×7 難局跑出 **6.01s**，
`--budget 20` 大盤裡單局跑出 **40.04s**。原因是 `stage_budget` 的語義是
「**每候選階段**牆鐘上限」：補缺宏吃一份 T，失敗後混合流水線再吃一份 T，
兩候選最多 2T；而 `GUI.py` 設置頁那行寫的是「求解時間上限（秒）」，
玩家填 20 實際會等到 40 秒。不是卡死，是參數語義和文案對不上。

修法＝新增 `total_budget`（整輪共享的單調 deadline），GUI 改傳它；
`stage_budget` 保留原義給 HTTP / 實驗基線對照。整輪 deadline 同時進
`out_of_time()`、補缺宏的 `cancel_check` 與混合的階段 `cancel_check`，
到點連正在跑的候選也退出、已播段照常有效。⚠️ **不能讓首候選吃滿整輪**：
探針裡 6×6 補缺宏超時後，混合還能在續算裡再播一段搜索段；所以首候選
最多占 `_TOTAL_SHARE_FIRST = 0.5`，餘額用絕對 deadline 自動讓渡給第二候選。
0.5 不是拍腦袋：6 局邊界案的份額敏感性對照（0.5 / 0.6 / 0.7）解出數
都是 1/6、牆鐘均值 18.49 / 18.46 / 18.38s 持平，部分成果 σ 均值
0.9669 / 0.9601 / 0.9567 單調遞減，故取均分。

**評估紀律（更容易錯的一層）**：只比「舊解出 N 局 vs 新解出 M 局」會
把「舊偷偷多等一倍時間」算成新語義的退化。必須加第三組
`stage_budget=T/2`（舊語義但總牆鐘同樣是 T）做**等牆鐘對照**。
T=3 壓力檔確實有 1/5 局「舊解出、新只回部分成果」（σ 1.000 → 0.960），
