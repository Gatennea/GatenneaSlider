# 三維求解器：借鑒原版混合求解器與公式生成器的結論

## 0. 一句話結論

1. **三維目前的瓶頸不是「什麼都沒搬」**：單次貪心之外已有 visited、預算、流式回調、歷史最優回退與三維專有的 mod 約束；缺的是分量級展開、流水線的三個關鍵層，以及「先量瓶頸再改」的證據。【修訂】
2. **公式生成器可以搬「生成、驗證、索引」的骨架，不能直接搬二維公式庫**。——這條原文成立，保留。
3. **三維公式庫應由三維求解軌跡自動挖掘，而不是把二維人類經驗翻譯成三維公式**。——這條原文成立，保留。
4. **任何改造前先確認目標**：項目定位是「炫技＋輔助找玩法＋數學目標，不是通用解」（`AGENTS.md` §0），解出率不該不作論證就當第一指標。【修訂】

## 1. 原版混合求解器為什麼快

### 1.1 分段聚攏，而不是一路貪心到底

`hybrid_solve(pipeline='alt')`：聚攏一小段（`alt_chunk=30`）→ 從起點重放驗證 → 只有提升才採納 → 最多 8 輪 → 推不動後交給後段。

**【修訂】原版實測 34.1s → 7.5s（約 4.5×，5×5 step2、8 seeds）不能直接歸因給「短段＋驗證＋切換」**：

- `docs/archive/混合求解器验收.md` 的消融寫得很清楚——拿掉填洞層，7.5s 漲到 12.7s（慢 69%），「兩者都留才最快」；提速主要來自「分段聚攏 ↔ 填洞宏交替」，不是分段本身。
- 這個數字是 2026-09-30 的歷史快照。當前 `solver/hybrid_solver.py` 文件頭記著：混合內填洞宏已於 2026-10-16 消融後移除，貢獻改由**獨立候選層「補缺宏」＋段3 GBFS** 覆蓋。`experiments/script_cap_reverify_alt.py` 更直接寫「兩代流水線結論相反，必須在當前代碼上重測」。
- 所以正確說法是：**「分段 + 交替 + 一個能快速改善局面的候選層」三者一起才快**，而且每一層都要在當前代碼上重新量。三維如果只搬「聚攏段 ↔ 逐洞段交替」，正好漏掉第三層。

### 1.2 逐洞 GBFS：每次只要求洞數減一

`search_core.guided_reduce_one()`：起點只算洞數、展開座標層合法動作、終止條件「洞數 < 本段起始洞數」、`canonicalize` 去重、父指針回溯、有 `node_budget` / `cancel_check` / `progress_cb`、每 256 節點讓出 GIL。這段原文成立。

**【修訂】還必須一起搬「單洞收口」**：`docs/solver/求解器設計.md` 記著，6×6 只改 idle budget 的解出率仍是 3/6，加上「兩候選跑完後用 `flow['end']` 重測、命中單洞補跑一次」才把那類局面收回（護欄 `test/_test_single_hole_closeout.py`）。**只搬預算不但不夠，還是項目明確踩過的坑。**

### 1.3 純座標 + 位棋盤展開

原版 `expand()` 不碰 `game` 物件：座標集合上枚舉每條縫兩側連通分量、bitboard 移位判連通、返回 `(新座標, action, rep_cell)`。三維現在每個候選 `snapshot → opt → try_move_ex → restore`，方向是對的。

**【修訂】三維的連通是 6 鄰接（Z³，`engine/lattice.py`、`engine/registry.py`），不是 26 鄰接**；設計 3D bitboard 時要把這一點寫進接口註釋，否則很容易誤用角/稜接觸當連通。

### 1.4 兩級評分：便宜 Φ 預篩 + 完整聚攏度終裁

原版 `gather_solve` 用 `profile_defect Φ`（約快 20×）對全部候選排序，只對前 `phi_prescreen_k=8` 個算完整 metrics，另有 `aggressiveness` / `stochastic` / `kick_moves` / `seed`。這段原文成立。

**【修訂】「每步對所有 action 跑完整 `cubic_metrics` 是最直接的效能痛點」是推測，不是結論**：目前沒有任何 `cubic_gather` / `cubic_metrics` 的 profiler 或牆鐘記錄。候選評估裡 `_apply_cubic_action`（`opt` + `try_move_ex` + `commit` + `restore`）和 `cubic_metrics` 誰佔大頭尚未量過；`cubic_gather.py` 已經把 `mod_constraints` 改成整場只算一次，原文明顯沒注意到。按項目紀律（端到端牆鐘複核、ABAB 配對），應先量再決定預篩要不要做。

### 1.5 工程底座：哪些已有、哪些沒有

**【修訂】原文說「三維沒搬工程底座」不準確。逐項對照 `solver/ml/cubic_gather.py`：**

| 底座 | 原版 | 三維 MVP 現況 |
|---|---|---|
| 去重 | 平移 + D4 canonical | 有 `visited`，但只是排序坐标 tuple，未做平移/對稱歸一 |
| 預算 | stage/total/idle | 有 `max_wait_time`、`patience`；無 idle / 共享 deadline / 雙候選隔離 |
| 流式 | `segment_cb` 邊算邊播 | 有 `progress_callback`（每步指標），但不是按段定稿的流式 |
| 部分成果 | `fill_partial` 回歷史最優 | 有 `best_snap`，未達標時回退到歷史最優並截斷動作 |
| 回傳 | `(actions, rep_cells)` | 有 `actions` / `rep_cells` / `trace` / `ignored_kwargs` 留痕 |
| mod 約束 | 二維 `detect_target_corner` | **三維專有 `cubic_mod_constraints` 已實現**（按 `(r%step,c%step,d%step)` 分佈鎖窗口起點餘數），原文完全沒提 |

`solver/ml/cubic_gather.py` 文件頭明寫「不承諾還原，不接查表/PDB/IDA*/混合；那些算法仍是二維語義，不能直接套到 (r,c,d)」——這是刻意的 MVP 邊界，不是漏搬。改造要補的是缺的那些層，不是把已有部分重寫一遍。

### 2.1 動作枚舉的三維缺口——只有一處是真的

**【修訂】原文列了四條「必須改」，其中兩條其實早已做好：**

- `cubic_gather_solve` 的返回字典**已經有 `rep_cells`**（`solver/ml/cubic_gather.py`）。
- `gui/events.py::_execute_cubic_macro_op` **已經優先用 `rep_cell` 調 `_find_block_by_cell()` 定位目標塊**，找不到才退回 `_find_block_on_side()`（同側首塊），正是原文要求的效果。

真正缺口只有一條：`enumerate_cubic_actions()` 對每個 `(gap_type, line, side)` 只產生一個動作，`_side_block()` 取該側第一塊；同一側若有多個連通分量，會漏動作或選錯分量。`engine/board.py::legal_moves()` 的註釋明確「每條縫每一側、每一連通分量」都要枚舉，求解器目前落後於引擎。

所以要做的是：補 `side_components_3d()` 枚舉每個分量、action 帶 `rep_cell`。注意求解器內部 action 是元組 `(gap_type, line, side, direction, rep_cell)`，而 GUI op 是 dict 且 `rep_cell` 是獨立欄位（`kind='cubic'`、`gap_type`、`gap_line`、`side`、`direction`、`step`），兩者別混為一談。

### 2.2 三維 canonical 的注意點——48 對稱與 mod 約束的衝突

原文「48 對稱是狀態去重用、目標盒只枚舉 6 種軸排列，兩者不要混」的提醒方向對，但沒說清怎麼不混。

**【修訂】`cubic_mod_constraints` 是開局算一次、假設整場滑動不變的 `(r%step, c%step, d%step)` 分佈；反射 (`r → L-1-r`) 一般不保持 `r % step`。** 若 `visited` 用 48 對稱（含反射）歸一後合併狀態，而打分仍用固定軸查 mod 約束，就會把對「鎖餘數窗口」並不等價的狀態折成同一 key。`cubic_gather.py::cubic_mod_constraints` 的註釋特意只保留 6 種軸排列、不引入反射/旋轉重複，正是為避開這點。

落地時二選一，不能兩個都要：（a）`visited` 只用平移歸一 + 6 軸排列，與 scoring 同口徑；（b）確實要 48 對稱，就連 mod 約束一起按對稱變換重算並證明等價。**在證明之前按 (a) 做。**

### 2.3 三維「洞」與「凸起」——前提要寫明

「塊數 = 目標盒體積 ⇒ 洞數 = 凸起數」只在**實心長方體目標盒**時成立。三維創造模式已支援自訂 `goal_pattern`（`engine/adapter.py::is_solved` 對 cubic 走 48 對稱 `canonical_key()`），自訂目標不是實心盒時這個等式不成立。因此：

- `cubic_metrics` 應回傳 `holes`、`outside`、`protrusion` 三個獨立值，不要假設兩者相等；
- 自訂目標的求解支援不能一直排在 P3——它是創造模式造出來的謎題目前的實際缺口。

## 3. 不要照搬的部分

1. **查表 / PDB / IDA\***：原版 PDB 只在有完整 BFS 表的尺寸上成立，跨尺寸有反例；三維沒有真值表，不要先上。
2. **學距離 / ML 打分**：原版實測否決；三維沒有資料支撐。
3. **並行多進程搜索**：原版預設關，實測 spawn + 序列化負收益；三維先單線程打磨。
4. **二維 `fill_macro.py` 逐行照搬**：它是方形幾何的共軛子宏，三維縫族、分量、洞型不同，只能借「局部宏 + 重放驗證」的思想。
5. **把「換終止判據」當成提升**：原版實測段變短但沒有更接近還原；三維要分開量「打分」和「終止」。
6. **二維目標 corner 公式直接套**：**【修訂】mod 不變約束的思想不只是「可移植」，三維版 `cubic_mod_constraints` 已經落地並有測試**（`test/_test_cubic_gather.py` 的 A2 段）。要做的不是「單獨寫」，而是把它接到新展開/新評分上，並按 §2.2 處理與 48 對稱的衝突。

## 4. 公式生成器：能搬骨架，不能搬公式庫

### 4.1 結論

- **可以搬**：共軛宏觀結構、宏觀動作語言、重放驗證、模板索引、生成器流程。
- **不能直接搬**：二維 `fill_macro` / `gap_solver` 裡的具體 `Setup` 步、角洞/邊洞分支、`A/B/C` 常數。
- **原因**：二維公式是「人類復原經驗的壓縮」，依賴方格、行列縫、轉置、角/邊洞、二維連通分量；三維是立體縫面、6 鄰接連通體、面/稜/角三類洞，直接翻譯大概率得到「看起來像公式、實際不成立」的東西。

### 4.2 可以保留的二維經驗（只作啟發，不作公式）

- 「先做準備，執行主操作，再逆回準備」的 `A[Setup]BCB′A′` 結構；
- 「先填角/邊，再填中心」的順序感，可改成三維「角/稜/面」順序假設，但必須驗證；
- 「不要破壞已固定區域」；「公式必須可重放」；「短解優先於亂走」。

### 4.3 三維公式生成器 v0：宏觀挖掘器（可行性有前提）

1. 對每個目標盒洞 `h`、盒外凸起塊 `p`，在目前盤面做深度 4–8 有界搜索；
2. 只允許不動「已固定區域」的動作；
3. 找到能把 `p` 填進 `h` 的短序列，記成一條局部宏；
4. 正規化局部形狀當模板鍵；
5. 大量打亂局面去重、排序、只留可重放且高命中率的模板；
6. 模板當成 `cubic_hybrid_solve` 的候選層，放在快速改善層之後、GBFS 之前。

**【修訂】第 2、4 步有兩個沒論證的難點，動手前要先小樣本驗證：**

- 三維一步是「切面某一側的連通片沿平行方向平移 step 格」，密集盤面下完全不碰已固定區域的合法動作可能極少，深度 4–8 未必湊得出填洞序列。要先量「符合約束的動作分支數」，別直接假設二維的深度夠用。
- 模板鍵同時要求「48 對稱正規化」又包含「可用縫面朝向 / 已固定區域邊界形狀」會互相抵銷：正規化的目的正是抹掉朝向，留下朝向鍵等於放棄去重。二選一——要泛化就只用正規化後的局部形狀，要精確就別做 48 對稱。

### 4.4 公式生成器的優先級

1. 三維單洞填補宏：對應二維 `solve_single_void`，只要求洞數減一。**【修訂】「最容易驗證」的前提是先有 §2.3 的 `holes` / `outside` 獨立指標**，目前 `cubic_metrics` 只回 `overlap`，要補。
2. 面/稜/角三類洞：驗證「角先、邊後」是否成立，不要假設。
3. 多洞聯合 / 整層宏、長公式 `A[Setup]BCB′A′`：最後做，每條都必須重放驗證。

### 4.5 資料來源

**【修訂】三維安全打亂不是「若走反向生成」的假設，而是已經落地**：`gui/cubic_create.py::_cubic_random_generate` 從實心還原態正向走，每步提交後驗證同縫反向能精確推回，整條路徑反轉就是解法，終態必有解。所以公式庫的收益定位是**解長、穩定、可讀**，不是「能不能解」——這點原文對，只是依據要寫對。

可從三維求解軌跡、安全打亂反向路徑、區域搜索成功序列挖掘局部宏；不需要先成為三維高手，讓求解器自己產生並驗證套路。

## 5. 建議落地順序（修訂：先量、補回關鍵層、再談高級改造）

### P0：量瓶頸 + 補真缺口

1. **先建 benchmark 與 profiler**：3×3×3 / 4×4×4 固定打亂集，記錄牆鐘中位/p95、解出率、解長、展開節點數；用端到端牆鐘確認 `cubic_metrics` 與 `_apply_cubic_action` 誰是大頭。**沒有這一步，後面所有優先級都是猜的。**
2. **先確認目標**：求解器是「炫技＋輔助」還是「盡量解出」？這決定要不要為了解出率投入公式庫。
3. 分量級 action + `side_components_3d()`（`rep_cells` 回傳與 GUI 回放已就緒，不用重做）。
4. `cubic_expand` 純座標展開 + 3D bitboard（6 鄰接）。

### P1：把已證實關鍵的層補回來

5. **快速改善候選層**（對應二維補缺宏）——原文漏掉，而這正是二维 4.5× 裡不可替代的那一層。
6. `cubic_guided_reduce_one`：每次洞數減一，先補 `holes`/`outside` 指標。
7. `cubic_gather_solve` 改短段 + 驗證提升；`cubic_hybrid_solve` 三層交替、共享預算。
8. **單洞收口 + 雙候選預算隔離 + idle budget**（三件一起，不能只搬預算）。
9. `segment_cb` 按段流式；`fill_partial` 已有 best_snap，補 score/Φ 擇優。

### P2：去重與評分（在 benchmark 證明有收益後）

10. canonical：先平移 + 6 軸排列；48 對稱要與 mod 約束一起證明等價後才上。
11. `cubic_profile_defect` 預篩 + top-k 完整 metrics；做之前先看二維的「步數減 40% 才開始省時間」門檻。
12. `stochastic / seed / kicks / aggressiveness`；`cubic_optimize_path` 重放驗證。

### P3：公式生成器與低優先

13. 三維單洞填補宏、面/稜/角模板分類（先做 §4.3 的兩項可行性驗證）。
14. 自訂 `goal_pattern` 求解支援（創造模式已能造這種謎題，別一直排在最後）。
15. 多洞聯合、整層宏、長公式。

## 6. 驗收口徑

每次改動至少看三個指標（順序按項目口徑：時間 > 解長）：

- **牆鐘**：中位數 / p95；
- **解出率**：固定打亂集上是否真的還原；
- **解長**：步數中位數，避免「解出但繞遠路」。

另外記錄：展開節點數、每段聚攏/逐洞/補缺宏的收益、失敗原因（`no_candidates` / `stuck` / `timeout` / `no_improve`）、使用的 seed 與參數。

沒有 benchmark 的「感覺變快」不算結論——這條原文對，修訂後把它落實到 P0 第 1 步。

## 7. 與現有代碼的銜接

現有鏈路：

`求解器產生 actions / rep_cells → gui/auto_solve.py 轉 macro_exec_ops → _execute_next_macro_step() → 三維 _execute_cubic_macro_op() → opt() → move_selected_blocks()`

改造後仍保持：

- 求解器只產生動作序列，不直接改盤面；
- 三維 op 契約不變：`kind='cubic'`、`gap_type=r/c/d`、`rep_cell=[r,c,d]`、`side=above/below`、`direction=六向`、`step=當前步長`；`rep_cell` 優先用於定位塊，失效退回同 side 首塊的邏輯已在 GUI 側；
- GUI 宏入口仍可保持「三維暫未開放宏功能」，但內部宏 op 執行器保留；
- 公式生成器的產物是「宏序列」，不是新的求解器分支。

## 8. 最後的判斷（修訂）

- 原版混合求解器的效率來自**多層協同**：分段聚攏 ↔ 一個能快速改善局面的候選層 ↔ 逐洞 GBFS，加上座標級展開、對稱去重、預算/流式/單洞收口。把 4.5× 全歸給「分段」是誤讀。
- 三維 MVP 已有簡化版的工程底座和三維專有的 mod 約束；真正缺的是分量級展開、快速改善候選層、單洞收口，以及在當前代碼上量出來的性能瓶頸。
- 先把 P0/P1 做完並有 benchmark 支撐，再判斷要不要投入公式生成器；它是「解長/穩定性」的加速器，不是三維求解器的第一步。
