# 三維求解器：借鑒原版混合求解器與公式生成器的結論

> 記錄日期：2026-11-19  
> 範圍：三維聚攏求解器（`solver/ml/cubic_gather.py`）的後續改造方向；原版二維混合求解器（`solver/hybrid_solver.py`、`solver/auto_solver.py`、`solver/search_core.py`、`solver/ml/gather_solver.py`）的借鑒點；三維公式生成器的可行性。  
> 性質：結論記錄，未改代碼、未新增求解器。

## 0. 一句話結論

1. **三維目前只搬了二維的「單次貪心聚攏」，沒有搬原版真正讓效率變高的「混合流水線 + 工程底座」。**
2. **公式生成器可以搬「生成、驗證、索引」的骨架，不能直接搬二維公式庫。**
3. **三維公式庫應由三維求解軌跡自動挖掘，而不是把二維人類經驗翻譯成三維公式。**

---

## 1. 原版混合求解器為什麼快

原版的效率不是來自某個單步啟發，而是五層一起工作：

### 1.1 分段聚攏，而不是一路貪心到底

`hybrid_solve(pipeline='alt')`：

- 聚攏一小段（預設 `alt_chunk=30` 步）；
- 立即從起點重放，驗證這一段是否真的讓聚攏度提升；
- 只有提升才採納，否則丟棄；
- 最多交替 8 輪；
- 聚攏推不動後，切到逐洞搜尋。

原版實測：5×5 step2、8 seeds，管線耗時 34.1s → 7.5s（約 4.5×），成功率不變。

三維現在的 `cubic_gather_solve` 是「240 步全局貪心，無改進就回歷史最優」，缺少這個「短段 + 驗證 + 切換」的層。

### 1.2 逐洞 GBFS：每次只要求洞數減一

`search_core.guided_reduce_one()`：

- 起點只算洞數；
- 展開座標層面的合法動作；
- 終止條件是「洞數 < 本段起始洞數」；
- `canonicalize` 去重；
- 父指針回溯，不複製路徑；
- 有 `node_budget`、`cancel_check`、`progress_cb`；
- 每 256 節點讓出 GIL。

三維對應：

- 洞 = 目標盒內未被佔據的格；
- 凸起 = 目標盒外的塊；
- 因為塊數 = 目標盒體積，洞數與凸起數相等；
- 三維只需要一個 `cubic_guided_reduce_one()`，每次讓洞數嚴格減一，不要把「直接還原」當成搜索目標。

### 1.3 純座標 + 位棋盤展開

原版 `expand()` 不碰 `game` 物件：

- 在座標集合上枚舉每條縫兩側的連通分量；
- 用 bitboard 整數移位做連通判定；
- 一次 `expand` 建一次網格，所有候選共用；
- 返回 `(新座標, action, rep_cell)`。

三維現在每個候選都 `snapshot → opt → try_move_ex → restore`，等於把遊戲物件當搜索狀態用。應該改成 `cubic_expand(coords, dims, step)`，搜索階段不碰遊戲物件、渲染、動畫。

### 1.4 兩級評分：便宜 Φ 預篩 + 完整聚攏度終裁

原版 `gather_solve`：

- 先算 `profile_defect Φ`（行列剖面 L1 偏差，約快 20×）；
- 只對 Φ 前 `phi_prescreen_k=8` 個候選算完整 `gather_metrics`；
- 用 `aggressiveness` 允許「比最佳低一點」的候選；
- 卡住時 `stochastic` 在 band 內 ε-greedy，必要時隨機踢 `kick_moves` 步；
- `seed` 保證可復現。

三維現在每一步對所有 action 都跑完整 `cubic_metrics`（重建 3D 前綴和 + 枚舉 6 朝向所有窗口），這是最直接的效能痛點。

### 1.5 工程底座：canonical、預算、流式、partial、路徑優化

- `canonicalize`：平移 + D4 對稱，`visited` 用 canonical key；
- `stage_budget` / `total_budget` / `idle_budget`：共享 deadline，無進展才停；
- `segment_cb`：每段定稿即上報，GUI 邊算邊播；
- `fill_partial`：全敗時回傳歷史最優部分成果；
- `_optimize_path`：去環、徘徊壓縮、遠程逆對抵消，最後重放驗證。

## 2. 三維可直接借鑒的清單

| 層面 | 原版做法 | 三維改造 | 優先級 |
|---|---|---|---|
| 流水線 | 聚攏短段 → 驗證 → 逐洞 GBFS 交替 | `cubic_hybrid_solve`：三維聚攏段 ↔ 三維逐洞段 | P1 |
| 動作枚舉 | 分量級 action + `rep_cell` | 掃同一側所有三維連通分量，每個分量一個 action | P0 |
| 展開 | 純座標 + bitboard | `cubic_expand` + 3D bitboard 連通 | P0 |
| 評分 | Φ 預篩，top-k 算完整指標 | `cubic_profile_defect` + top-k `cubic_metrics` | P0 |
| 去重 | 平移 + D4 canonical | 平移 + 48 立方對稱 canonical | P0 |
| 隨機性 | `aggressiveness` / `stochastic` / `seed` / `kicks` | 照搬語義 | P0 |
| 預算 | `idle_budget`、共享 deadline | 三維 idle 停機 + 分段共享預算 | P1 |
| 流式 | `segment_cb`，邊算邊播 | 三維分段回調，接現有宏 op 執行器 | P1 |
| 部分成果 | `fill_partial` + score/Φ 擇優 | 三維 partial 快照 + 洞數/聚攏度 | P1 |
| 路徑優化 | 去環、徘徊壓縮、遠程逆對 | `cubic_optimize_path`，重放驗證後才採用 | P2 |

### 2.1 動作枚舉的三維缺口

原版 `apply_with_rep()` 明確解決「同一側有多個連通分量」的歧義：

- 動作是 `(gap, line, side, direction, rep_cell)`；
- `rep_cell` 選中包含它的連通分量。

三維 `enumerate_cubic_actions()` 目前只枚舉 `(gap_type, line, side, direction)`，`_side_block()` 取該側第一塊，等於每個側面只考慮一個分量。同一側若有多個分離塊，會漏動作，也可能選錯分量。

必須改：

- 三維 `side_components_3d()` 枚舉每個分量；
- action 擴成 `(gap_type, line, side, direction, rep_cell)`；
- 求解器回傳 `rep_cells`；
- 回放優先使用 `rep_cell`，失效才退回同側首塊。

### 2.2 三維 canonical 的注意點

- 平移不變：包圍盒最小角歸原點；
- 48 對稱：立方體旋轉/反射取最小 key；
- `visited`、最佳快照都用這個 key；
- **48 對稱是狀態去重用；目標盒只枚舉 6 種軸排列，兩者不要混。**

### 2.3 三維「洞」與「凸起」

- 目標盒內未佔格 = 洞；
- 目標盒外的塊 = 凸起；
- 塊數 = 目標盒體積時，洞數 = 凸起數；
- `cubic_metrics` 應直接回傳 `holes`、`outside`、`protrusion`，而不是只回 `overlap`。

## 3. 不要照搬的部分

1. **查表 / PDB / IDA\***：原版 PDB 只在有全量 BFS 表的 4_4_2 / 4_4_3 上成立，跨尺寸有反例；三維沒有真值表，不要先上。
2. **學距離 / ML 打分**：原版已實測否決；三維沒有資料支撐。
3. **並行多進程搜索**：原版預設關，實測 spawn + 序列化負收益；三維先單線程打磨。
4. **二維 `fill_macro.py` 逐行照搬**：它是方形幾何的共軛子宏，三維縫族、分量、洞型不同，只能借「局部宏 + 重放驗證」的思想。
5. **把「換終止判據」當成提升**：原版實測段變短但沒有更接近還原；三維要分開量「打分」和「終止」。
6. **二維目標 corner 公式直接套**：mod 不變約束的思想可移植，但三維的軸、窗口、殘餘判定要單獨寫。

## 4. 公式生成器：能搬骨架，不能搬公式庫

### 4.1 結論

- **可以搬**：共軛宏觀結構、宏觀動作語言、重放驗證、模板索引、生成器流程。
- **不能直接搬**：二維 `fill_macro` / `gap_solver` 裡的具體 `Setup` 步、角洞/邊洞分支、`A/B/C` 常數。
- **原因**：二維公式是「人類復原經驗的壓縮」，依賴方格、行列縫、轉置、角/邊洞、二維連通分量。三維是立體縫面、三維連通體、面/稜/角三類洞，直接翻譯大概率會得到「看起來像公式、實際不成立」的東西。

### 4.2 可以保留的二維經驗（只作啟發，不作公式）

- 「先做準備，執行主操作，再逆回準備」的 `A[Setup]BCB′A′` 結構；
- 「先填角/邊，再填中心」的順序感，可改成三維的「角/稜/面」順序假設，但必須驗證；
- 「不要破壞已固定區域」；
- 「公式必須可重放」；
- 「短解優先於亂走」。

### 4.3 三維公式生成器 v0：宏觀挖掘器

1. 對每個目標盒洞 `h`、每個盒外凸起塊 `p`，在目前盤面上做深度 4–8 的有界搜索；
2. 只允許不動「已固定區域」的動作；
3. 找到能把 `p` 填進 `h` 的短序列，就記成一條局部宏；
4. 用 48 對稱 + 平移把「局部形狀」正規化，當模板鍵；
5. 在大量三維打亂局面上跑，去重、排序、只保留可重放且高命中率的模板；
6. 把模板當成 `cubic_hybrid_solve` 的候選層，放在聚攏段之後、GBFS 之前。

模板鍵建議包含：

- 目標盒局部佔位形狀；
- 洞的類型（面/稜/角）；
- 凸起塊的相對位置；
- 可用縫面朝向；
- 已固定區域的邊界形狀。

### 4.4 公式生成器的優先級

1. **三維單洞填補宏**：對應二維 `solve_single_void` 的三維版，只要求洞數減一，最容易驗證。
2. **面/稜/角三類洞**：自然長出三維版的「角先、邊後」經驗。
3. **多洞聯合 / 整層宏**：需要更多資料，晚做。
4. **長公式 `A[Setup]BCB′A′`**：最後做，且每條都必須重放驗證。

### 4.5 資料來源

- 三維安全打亂若走反向生成，可解性已有保證；公式庫的收益是**解長、穩定、可讀**，不是「能不能解」。
- 可從三維求解軌跡、反向打亂路徑、區域搜索的成功序列中挖掘局部宏；
- 不需要先成為三維高手，讓求解器自己產生並驗證套路。

## 5. 建議落地順序

### P0：工程底座

1. `cubic_expand` 純座標展開 + 3D bitboard 連通；
2. 分量級 action + `rep_cell`；
3. 3D canonical key（48 對稱）；
4. `cubic_profile_defect` 預篩，top-k 才算完整 metrics；
5. 接上 `stochastic / seed / kicks / aggressiveness`。

### P1：混合流水線

6. `cubic_gather_solve` 改成「短段聚攏 + 驗證提升」；
7. `cubic_guided_reduce_one`：每次洞數減一；
8. `cubic_hybrid_solve`：聚攏段 ↔ 逐洞段交替，共享預算；
9. `segment_cb` / partial / idle budget。

### P2：公式生成器與收尾

10. 三維單洞填補宏；
11. 面/稜/角模板分類；
12. 路徑優化；
13. benchmark：3×3×3 / 4×4×4 打亂局面成功率、步數、牆鐘。

### P3：低優先

14. 自訂 `goal_pattern` 目標集合（不再只支持實心長方體目標盒）；
15. 多洞聯合、整層宏、長公式。

## 6. 驗收口徑

每次改動至少看三個指標：

- **解出率**：固定打亂集上是否真的還原；
- **牆鐘**：中位數 / p95；
- **解長**：步數中位數，避免「解出但繞遠路」。

另外記錄：

- 展開節點數；
- 每段聚攏/逐洞的收益；
- 失敗原因（`no_candidates` / `stuck` / `timeout` / `no_improve`）；
- 使用的 seed 與參數。

沒有 benchmark 的「感覺變快」不算結論。

---

## 7. 與現有代碼的銜接

現有鏈路：

`求解器產生 actions / rep_cells → gui/auto_solve.py 轉 macro_exec_ops → _execute_next_macro_step() → 三維 _execute_cubic_macro_op() → opt() → move_selected_blocks()`

改造後仍保持：

- 求解器只產生動作序列，不直接改盤面；
- 三維 op 契約不變：`kind='cubic'`、`gap_type=r/c/d`、`rep_cell=[r,c,d]`、`side=above/below`、`direction=六向`、`step=當前步長`；
- GUI 宏入口仍可保持「三維暫未開放宏功能」，但內部宏 op 執行器保留；
- 公式生成器的產物是「宏序列」，不是新的求解器分支。

---

## 8. 最後的判斷

- **原版混合求解器的效率主要來自「分段 + 逐洞 GBFS + 座標級快速展開 + 對稱去重 + 預算/流式」，不是某個單步啟發。**
- **三維現在只學了最後一層的貪心；先把前四層搬過來，收益會比繼續調 `score` 大得多。**
- **公式生成器值得做，但它是「解長/穩定性」的加速器，不是三維求解器的第一步；先讓三維求解器有可用的混合流水線，再從它的軌跡裡挖公式。**
