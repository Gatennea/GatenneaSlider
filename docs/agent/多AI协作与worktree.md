# 多 AI 協作與 worktree 工作流（2026-11-13 用戶拍板）

多個 AI 並行開發同一倉庫的分工模型：**主目錄獨佔 `main`，其他 AI 各開 worktree**。
比「每個 AI 各自 clone 一份」好在：對象庫只有一份（省磁盤）、fetch 一次所有目錄共享、分支天然隔離。

## 1. 分工模型

- **主目錄** `E:/program_project/other/wkbddtest/GatenneaSlider` 檢出 `main`，由管 main 的 AI 獨佔：
  負責合併、合併後測試、（經用戶決策）推送。**主目錄只做合併與同步，完全不改代碼**——
  管 main 的 AI 自己要改代碼時，同樣開 work 分支 + worktree，改完測完自己並回。
  例外：純文檔小改（紅線 / 索引 / 待辦登記）允許主目錄直接改並**立即提交**（停留分鐘級，
  `git add` 指定文件、不捲入他人半成品）。其他 AI **不得在自己目錄操作 main**
  （物理隔離：main 只在主目錄檢出，其他 AI 想誤提交都做不到）。
- **所有 AI（含管 main 的）改代碼一律走 worktree**：每個工作點一個目錄 `GatenneaSlider-<後綴>`，檢出自己的分支開發。
- **worktree 側 AI 的動作邊界：只做本地 commit**（在自己分支上提交，含跑測試、落盤產物）——**不推送、不合併**。
  合併由管 main 的 AI 統一執行（§3）；推送經用戶決策後，同樣由管 main 的 AI 走網關執行。
  在自己目錄 checkout / 操作 main 一律禁止（main 只在主目錄檢出）。
- 現有範例（2026-11-13）：`GatenneaSlider-geo` → `feat/geometry-engine`、
  `GatenneaSlider-math` → `feat/math-research`（數學長分支，不合完即刪）、
  `GatenneaSlider-reuse` → `topic/solver-reuse-refactor`、
  `GatenneaSlider-doubao`（`E:/program_project/other/doubaotest/slider`，原獨立 clone 改掛）→ `feat/doubao-scratch`。

## 2. worktree 基本操作

```bash
# 新建 worktree：新目錄 + 新分支，一條命令
git worktree add E:/.../GatenneaSlider-<後綴> -b feat/<主題>

# 列出所有 worktree
git worktree list

# 正確刪除（目錄裡有未提交改動會拒絕，防丟）
git worktree remove <目錄路徑>

# 目錄已被手動刪掉時，主倉庫跑這個清登記
git worktree prune
```

兩條硬規則：

1. **同一分支不能同時檢出到兩個目錄**（git 直接拒絕，這是保護不是障礙）。
2. **刪 worktree 必須走 `git worktree remove`**，別直接刪文件夾；已手動刪過的跑 `git worktree prune` 清登記。

## 3. 合併紀律（管 main 的 AI 執行）

0. **合併前置檢查：主目錄 tracked 工作區必須乾淨**（`git status --short --untracked-files=no` 為空）。
   主目錄可能被多個會話共用——別人的半成品（` M` 狀態）在場就**等它提交完再合併**，不搶窗口。
   理由：①merge 改動若與半成品文件相交，git 直接拒絕，白跑；②底座測試 import 的是帶半成品的工作區，
   好壞歸因會混（2026-11-13 靠「先採基線」倖免，這是臨時手段不是規則）；③最險的一種：merge 進行中
   對方 commit 推進了 HEAD，merge commit 的樹快照會**把對方已提交的內容回退掉**——不報錯、事後才炸。
1. **完成標準**：分支上功能完整 + 護欄測試通過，才通知合併——**不是每 commit 一次就並一次**
   （並得頻繁單次衝突小，但測試輪次暴增；按「完整功能」粒度並最省事）。
2. **合併串行**：一次只並一個分支；並完跑底座測試（`pytest test/ --collect-only -q` + compileall +
   三項 lint，見 `readme_to_agent.md` §9.2）確認沒炸，再並下一個。並行並兩個分支會讓衝突疊加。
3. **合完即刪**（沿用 `AGENTS.md` §7 既有約定）：合併後刪分支 + `git worktree remove`。
   `feat/math-research` 是長分支，例外不刪。
4. **衝突處理**：小衝突管 main 的 AI 直接解；大衝突（同文件兩邊大改）優先讓分支歸屬的 AI
   自己 rebase 到最新 main 後重新提出，不硬解。
5. **合併時同步核銷待辦文字（2026-11-17 用戶指出漏洞）**：分支交付若完成了某節待辦，
   管 main 的 AI **合併當下就把對應節從 `待办清单.md` 整節刪掉**，別只合程式碼、留著文字——
   事後很難記得回來删。實例：§43（特大尺寸卡頓）的修復 `bbaf7cf`/`5ce5ccf` 早已合進 main，
   節卻還掛著；§25 標題已寫「已處置」、正文 ALL PASS 也一直沒删。核銷前按 §5「是否真做完」
   核實程式碼與提交，完成記錄走 git log / 當日日誌。分發新一輪前先掃一遍全表，
   把「已做但文字還在」的節清掉，避免帶著髒總賬分發。
6. **推送不變**：仍走「審後提交、不擅自推送」，push 由用戶 / 網關決策，合併進 main 不等於可推送。
7. **【2026-11-19 加：寫權與併發】**：
   - **角色 ↔ 路徑綁定**：主目錄只在 `main` worktree 動紅線文件；各 AI 只在**自己的**
     worktree / 分支寫。管 main 的 AI 去別人的 worktree 同步時，只准做 merge / 唯讀巡檢，
     **不得直接在別人工作區改文件或 checkout 丟棄改動**（2026-11-19 曾在 dev 正被 trae 使用時
     checkout 掉它工作區的待辦中間態）。
   - **開工第一步自報**：每個 AI 開工先講「我的路徑 + 分支 + 角色」，別人據此避讓；
     判不了某工作區是否有人在寫，就先問，別直接進去動。
   - **提交前核對暫存區只含本會話產出**：`git diff --cached --stat` 逐項看一遍再 commit；
     別人的半成品 / 別的會話的中間态一份都不裹進來（trae 2026-11-19 靠這條沒誤提交）。

## 4. 各 AI 需要知道的差異

- **config 運行態 / build / dist 各目錄獨立**：worktree 裡跑測試、清運行態**不會碰到主目錄用戶
  正在玩的實例**（隱藏好處）；但 build / dist 是空的，打包要各自重建。
- **求解器查表 / ML 數據不隨檢出過來**：`solver/data/`、`solver/ml/data/` 被 `.gitignore` 擋住，
  新 worktree 檢出後只有代碼與文檔（實測約 20MB），這兩個目錄是空的。要用查表 / ML 功能就從主目錄
  複製現成表（約 600MB），**別重跑建表**（耗時且容易和主目錄數據版本漂移）。
- **分支快照滯後**：AGENTS.md / docs 在該 AI 開工那一刻定格，main 上新合入的約定**不會自動出現**
  在其目錄。重要約定更新後，各 AI 開工前先 `git merge main`（或由管 main 的 AI 在合併時提醒同步）。
- **untracked 大產物別堆 worktree**：experiments 產物 / 打包輸出用完即清，
  別積到只能 `git worktree remove --force` 的地步。

## 5. 待辦集中分發（2026-11-14 用戶拍板）

**`docs/agent/待办清单.md` 是未完成事項唯一總賬，也是任務分發的唯一入口**：新增待辦一律由
管 main 的 AI 在**主目錄直接寫入並立即提交**（屬 §1「純文檔小改」例外的具體化）。用戶提出的
新待辦由主目錄集中登記，同步到各 worktree 後再由用戶口頭通知各 AI 認領——分發與執行解耦：
總賬只在 main 上動，各 AI 只在自己分支上執行。

- **worktree 側 AI 一律不改待辦清單**：不新增、不刪節（核銷）、不改狀態。完成某節時只在
  合併通知 / commit message 註明「完成了 §N」，由管 main 的 AI 在合併時核實程式碼與提交後
  統一刪節。理由：①多寫者改同一文件必然在合併時撞車；②「是否真做完」應由合併者核實，
  不是開發者自己劃掉。
- **分發流程**：①主目錄寫入 + `git add` 指定文件 + **立即 commit** → ②各 worktree 目錄
  **tracked 工作區乾淨**時同步：無獨有提交用 `git merge --ff-only main` 快進，已有自己的
  提交用 `git merge main`；有半成品在場就等，別硬來 → ③用戶通知各 AI 認領。
  **分支快照滯後**：沒同步前別人看不到新待辦，所以「同步」是分發的一部分，不是可選項。
- **推送另算**：以上是本機各目錄同步；推到遠端仍走 `AGENTS.md` §7「審後提交、不擅自推送」，
  由用戶決策、管 main 的 AI 走網關執行。
- **寫法紀律不變**：號碼 = 現有最大值 + 1、**追加在文件末尾**、只放未完成、保留用戶原話
  （見 `docs/agent/待办清单.md` 開頭「怎么用」）。
- **分支上已有待辦改動時**：合併以 main 版為準，分支側對該文件的改動一律丟棄（請分支歸屬
  的 AI 先自行撤掉），不把兩版併起來。
- **【2026-11-19 加：紅線文件異常條款】**：在任何非 main worktree 發現紅線文件
  （`docs/agent/待办清单.md`、`AGENTS.md` / `agents.md`、`docs/README.md`、`experiments/INDEX.md`）
  出現**未提交改動**＝**異常事件**，不是正常協作提醒——即便內容只是換行/跳脫字元等噪音也一樣。
  發現者：**不 staged、不提交、不自行判噪音丟棄**（2026-11-19 就有人把別的會話的待辦中間態
  當噪音 checkout 掉）；先在回報裡**明確定性地為異常**，附路徑與分支，由用戶/管 main 的 AI 判定。
  技術兜底（待實裝，先立條款）：非 main 分支提交待辦清單應被 pre-commit 鉤子拒絕，
  把「只有主目錄能改」從約定升級為強制。

## 6. 認領佔位 + 分支私有筆記（2026-11-17 用戶拍板）

上一節「worktree 側一律不改待辦清單」放得太寬會丟資訊、收得太緊又會撞車，改成**總賬唯一 +
分支各有筆記**兩層：

- **認領佔位（防撞車）**：自由更新保留，但開工前須認領——在**自己分支的私有筆記**寫下
  「認領 §N」，別人看到即繞開；若不得不碰同一處（如兩個 AI 都盯上 `_think_find_move`），
  先經用戶協調，別各自埋頭改。2026-11-17 的 §43 就是兩個 AI 各寫一版互斥實現，合併時
  函數級衝突、`-X ours` 還混出 `NameError`，一版白寫並回退。
- **公共文件仍歸主目錄獨佔**：待辦清單、`agents.md`（紅線）、`experiments/INDEX.md` 等
  全體共用文件，worktree 側一律不改（延續 §5）；改這些 = 合併必撞。
- **分支私有筆記**：每個分支在 `docs/agent/分支笔记/<分支名>.md` 記認領、開發中發現的新問題、
  驗證結論——worktree 側對**自己這份文件**有完整寫權，不必再靠口頭或 commit message 傳遞。
  主目錄合併 / 巡檢時讀各分支筆記：認領資訊用來避讓，新發現由主目錄判斷是否提升為總賬正式待辦。
- **防腫脹**：筆記只放「在辦 + 未決發現」，完成的條目隨分支合併後清掉；使用者日常只讀總賬一份。
- **【2026-11-19 改：筆記隨合併進 main，不再人肉排除】**：舊做法要求「筆記不進 main」，靠
  「合併時手動撤出 + 同步後手動恢復」維持，但 ff-only 同步會把 main 沒有的 tracked 檔刪掉，
  兩次丟筆記、三個分支各留一個「同步 main 後恢復」提交，全靠人記。改成：
  **筆記隨分支正常合併進 main，main 上當噪音、不維護、不當總賬**；合併時**不再** reset / 撤出 /
  歸檔 / 恢復，`git merge --ff-only` 照常用。合完即刪分支時，筆記留在 main 的歷史裡，不必再清。
  取捨：main 的分支筆記目錄會有多份別的分支筆記，這是預期噪音，別當待辦讀。
- **同步後不用再核查筆記**：上面改成自然進 main 後，「同步後確認筆記還在」這道收尾作廢；
  若某分支仍沿用舊習慣自己撤/恢復，主目錄合併時直接保留、不幫它排除。
