# 多 AI 协作规定（人读版）

> 受众：拍板、分发任务的人。这是 `多AI协作与worktree.md`（AI 版）的精简总结。
> git 命令、合并步骤、测试口径等细节看 AI 版，本文只讲人需要知道和遵守的。

## 这套流程在做什么

只有一份仓库、一个主线。主线目录管 `main`，负责合并、同步、登记待办，**不写业务代码**；
其他 AI 各在一个独立目录里开发，做完一整块功能交回来合并。连管主线的人自己要改代码，
也得另开 work 分支，不能在主目录直接改。

## 三条边界

1. **主线只合并、不写码**；各 AI 只提交，不推送、不合并。
2. **公共文件只有主线能改**：待办清单、`agents.md`（红线）、实验索引。人人能改，合并必然撞车。
3. **同一件事只给一个 AI**，开工先认领占位；撞到同一处要事先招呼。这次 §43 两个 AI 各写一版
   `_think_find_move`，一版白写还得回退，就是没占位。

## 你平时要做的

- **提待办**：你说 → 主线写进总账并立即提交 → 同步各分支 → 你再通知 AI 认领。
  别绕开总账直接派活，否则谁在做什么是一本糊涂账。
- **等交付再合**：功能完整 + 护栏测试过了才算完成，不是每提交一次就合；合完主线跑底座测试，
  确认没炸再往下。
- **发版另说**：合进 `main` 不等于能发布，推送要你单独拍板。

## 待办怎么分层（解决"太严"和"臃肿"）

- **总账唯一**：`待办清单.md` 仍是唯一总账，主线独占、只放未完成，增删核销都由主线做。
  这条不变——它是任务分发的唯一入口。
- **分支有自己的笔记**：每个 AI 另有一份自己的笔记，认领了什么、发现了什么新问题、验证了什么
  结论，都可以自由记。开发中发现的问题不再"没地方写，只能口头说"。
- **笔记要瘦**：只放在办和未决的；做完随分支合完就清掉，文件跟分支走。主线巡检笔记时，把值得
  跨分支处理的新发现提升为正式待办。这样你日常只读总账一份，不会多出几份清单要维护。

## 红线

- worktree 侧不合并、不推送；主线不做业务改动。
- 不用 `git add -A` / `commit -a`，会卷进别人的半成品。
- 合并前主线工作区必须干净，有半成品就等，别抢窗口。
- AI 不删改待办总账；自己的发现写自己笔记。
- 合并不等于可发布。
