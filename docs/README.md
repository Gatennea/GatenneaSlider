## 狀態標註紀律

> **一份文檔「做到哪一步」只在本文件「狀態」列維護；文件頭不准自述完成度。**
> 理由：文件頭自述會隨落地推進滯後，索引再抄一份就變成三處口徑
> （文件頭 / 索引 / 待辦）；2026-11-13 清掉的 785 行留檔即是後果。
> **文件頭仍可留**：受眾、記錄日期、關聯文檔指針、實驗背景、當次實測原始數據
> ——這些回答「這份文檔是什麼」，不是「做到哪一步」。
> **不准留**：`P0/P3 已完成`、`M0–M4 已執行`、`S5 已通過`、`待補 XX`、`未開始`
> 這類進度句；要寫就改成本文件狀態列一格，或一句指針「現狀見 `docs/README.md`」。
> 狀態列**建議**取值：`維護中` / `草稿` / `快照` / `投稿用` / `對外` / `留檔`；
> 系列文檔（如夜間實驗）在「用途」欄標「系列 ① ②」並統一日期後綴，不靠檔名猜新舊。
> 存量措辭不逐一批改：**改到哪份就順手收編哪份**。

### 計畫類文檔完成後的去向

> **「計畫 / 方案 / 設計」類文檔是為了解決某條待辦而寫的，不是待辦本身。**
> 對應功能落地、待辦核銷後，這份文檔要**及時清出活文檔區**，否則會和真待辦混淆、
> 讓 AI 誤以為還有活沒做完。去向按有無**後續參考價值**二選一：
> - **有**（記錄了機制口徑、取捨理由、實測數據、踩坑）→ 移到 `docs/archive/`，
>   狀態標 `留檔`，**內容不改**（要改就在標題或 README 註明「已完成，留檔」）。
> - **沒有**（只是當初的步驟安排，落地後無人再查）→ 直接刪。
> **別因為「留著以防萬一」就堆在原地**——git 歷史隨時能翻出舊版，移到 archive 也仍在庫裡。
> 例：`docs/archive/安全打乱_2026-10-18.md` / `docs/archive/打乱演示动画_2026-10-18.md` /
> `docs/archive/前端動效優化計劃_2026-11-17.md`（S0–S7 已收尾：已落地的落地、其余用户拍板不做）。
> 移档后**全倉反引號路徑要同步改**（見 `docs/agent/踩坑与搁置.md` doclink NEW 條）。
