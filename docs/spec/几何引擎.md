## 0. 说人话

今天的代码里，「方形 / 三角 / 米字」是三套各自为政的引擎，靠一堆同名方法
（`opt` / `try_move_ex` / `commit_move` / `is_solved` …）粘在一起，上层
到处是「如果是三角就…如果是米字就…」的分支。

这个方向要把「密铺形态」本身变成**一份数据**（板型）：新谜题 = 写一份
板型定义（代码基石）+ 在 GUI 上画出来，引擎负责回答「这谜题能不能玩」——
**有没有锁死的缝、会不会冻形、能不能打乱**。坐标 / 邻接 / 缝隙 / 移动 /
还原判定全部按任意维度设计，三维只是再填一份参数的事。

这不是推翻重来：三种异形已经把几何拆得挺开，数学文档也已经给出了统一
抽象（板型 B），求解器里甚至已有一个形态无关的骨架。P0 原型证明了路
走得通——**引擎与现有方形引擎在移动 / 规范形 / 还原判定上逐项全等**，
且核心代码对维度无感（同一份核心跑三维立方晶格）。

## 1. 愿景与范围

**几何引擎 = 游戏核心逻辑的引擎级架构**，具体四件事：

1. **自定义滑块形状与密铺规则**：一种新谜题 = 一份「板型」数据
   （格空间 + 朝向 + 方向 + 缝族 + 还原态 + 块数），注册即用。
2. **三维预留**：坐标是任意维度整数元组，邻接 / 缝 / 移动 / 规范形 /
   还原判定全部维度无关；三维谜题 = dim=3 的板型（原型已演示立方晶格）。
3. **定义新谜题的两条路**：代码写板型（基石，精确）；GUI 上绘制格子
   （板型的 `cell_polygon` 钩子给出纯几何多边形，绘制层据此渲染——
   两者产出同一份数据，不搞两套真相）。
4. **规则自检**（引擎的体检报告）：定义新谜题时先问引擎——
   - 有没有**锁死的缝**？（米字双重晶格错位态下横竖缝整条穿过块内部，
     就是这类问题的原型案例）；
   - 会不会**冻形**（零合法移动，保存前必须拦截）；
   - 能不能**打乱**（从还原态可达的形状太少 = 这规则打不开；可逆打乱
     保证终态有解）。

**明确不做**：不推翻现有三引擎（P1 之前 main 行为零变化）；不承诺求解
器对新板型自动生效（`SOLVER_FORM_SUPPORT` 显式声明，异形选到不支持的
算法明确拒绝——AGENTS.md §2 延续）；引擎保持纯逻辑零 pygame（§10 延续）。

## 2. 参考实现：Geraniums Pot（已拉源码研究）

**它是什么**：pygame 写的开源「相交圆盘」平面魔方模拟器（旋转类，不
是滑块类）。本机发行版在 `E:\Geraniums Pot`（**只读，禁止修改**）；源
码已克隆到仓库外参考目录（`github.com/grigorusha/GeraniumsPot`）。

**架构上对我们有价值的五条**：

1. **谜题 = 文本脚本 → 通用数据结构**。约 40 条行式命令（`Ring` /
   `Line` / `Arch` / `Part` / `AutoCutParts` / `Latch` / `Linked` /
   `CopyParts` / `MirrorParts` …）解析成 rings / archs / parts / lines
   四张表。同一份引擎代码跑遍全部谜题——「数据定义的谜题」在 pygame
   体量下完全可行，这是本方向最直接的先例。
2. **块 = 边界表示**（弧 + 线段的链 `arch_lines`）+ 精简多边形（快速
   相交检测）+ 样条（绘制）。形状不受网格限制——我们的板型目前是格点
   式，但 `cell_polygon` 钩子同思路：几何与规则分离。
3. **移动 = 对几何选出的子集施加变换**：圆内的零件整体旋转。合法性 =
   几何判据（包含性、旋转后圆非空 = 我们的「两端非空」）。与我们的
   「选缝 → 取一侧连通分量 → 平移」同构，只是变换从平移换成旋转。
4. **Latch（闩）= 数据化的捆绑**：零件带方向锁，同一圆内出现反向闩则
   锁死——与我们的捆绑组（`Block.group`，缝切不开组）同思想，且它是
   **纯数据字段**，这支持我们把捆绑提升为板型级能力。
5. **静态几何体检**：零件重叠检测（`fl_error` 红框警示）、圆与零件
   包含性检查——自定义谜题加载时先体检，与我们要做的「锁死缝 / 冻形
   / 可打乱性预检」是同一类事。

**它的局限（我们不学的部分）**：连续旋转语义（我们是离散格点状态机，
数学体系整个建立在离散上）；无求解器；打乱是纯随机、不保证有解
（我们的安全打乱 2026-10-18 就已做到「每步可逆 ⟺ 终态有解」）；还原
态靠存截图而非计算判定。

## 3. 现状评估（代码调研结论，2026-10-20）

三份并行调研（几何层 / 求解器层 / Geraniums Pot 源码）的事实摘要：

**已经站在我们这边的**：
- 同名契约（`opt` / `try_move_ex` / `commit_move` / `is_solved` /
  `shuffle` / `all_gaps` / `side_has_blocks`）已承担接口角色，上层
  （GUI move/drag/events、求解器、安全打乱三函数）全靠它统一驱动；
- `solver/ml/shape_gather.py` 的 `ShapeGather` 骨架 + tri/mi 适配器
  已是**形态无关协议 + 每形态实现**的雏形（coords_of / shape_score /
  enumerate_actions / apply_action / snap / restore 六件）；
- 安全打乱三函数（`game.py:104-195`）是模块级形态无关实现——解耦路线
  在本仓库已被验证可行；
- 数学文档已给出统一抽象「板型 B = (Λ×Ω, D, Σ, S₀, K)」，且证明守恒
  着色 = 平移格子 Δ 的陪集 × 朝向，三种现有形态是同一公式的特例；
- `gui/cell_class.py` 已是三形态统一的不变量公式。

**硬骨头（按硬度排序）**：
1. `Block.location` 是变长 list、分量语义随形态隐式变化（三角第 3 分量
   是 up、米字是 q）——引擎用显式 `(point, orient, group)` 三元组解决；
2. 缝隙词汇表 / side 口径三形态不统一（h/v vs h/p/n vs h/v/d1/d2；
   词 vs 0/1）——引擎用「线性泛函 + 符号侧」统一，词汇表随板型注册；
3. 米字双晶格 + 半整数 + SAT 重叠无类比物——`seam_clear` 钩子预留
   （span 锁死判据），半整晶格用 scale=2 + 奇偶约束表达；
4. GUI 约 60 处旗标三分派（renderer / events / move / drag /
   animation）+ 三个 view 类无共同接口——最大工作量在 P3；
5. 求解器方形专用件（table_core / search_core / actions / state /
   heuristic）整体假设 2-tuple + D4 + h/v——泛化或维持适配器现状需决策；
6. history 靠 `hasattr` 嗅探类型（`hasattr(game,'k')` 认三角）——引擎化
   后类型信息显式化；
7. **同点多朝向联合键**（P2 已解决，2026-10-21）：局面唯一性键 =
   `(point, orient)`——`Board.keys` / `block_map` / `Move.moved` 全部
   按键寻址；方形退化为 `((r,c), '')`，与 P0 逐项同形；
8. **orient 进规范形**（P2 已解决）：`canonical_key` 做 `(point, orient)`
   联合变换——每个自同构除搬点外还按 `orient_dirs` 诱导朝向置换；米字
   合法移动依赖 orient，只规范化点集会让「旋转后的同一局面」漏等价；
9. **米字对角缝的朝向相关侧判定**（P2 已解决）：`SeamFamily.rank` 钩子
   `(point, orient) → int`，四族 rank 全带朝向修正（h/v 的 N/W 扣半格、
   d1/d2 按朝向分侧）；配套 `line_scale` 记录「引擎缝号 t 与外部线号 L」
   的换算（米字 h/v = 4×，错位态有 ¼ 线）。

## 4. 可行性结论

**可行，且已用差分测试逐期证明**（`feat/geometry-engine` 分支，
`engine/` 包 + `test/_test_geometry_engine.py`：A–M 全绿（显式断言约
150 项）+ `test/_test_engine_adapter.py` N 节钉死开关与适配器等价；
全套回归无新增失败）：

- **模型**：板型 = 五件套数据（格点 Λ / 朝向 Ω / 方向 D / 缝族 Σ /
  还原态 S₀）；局面 = 不可变块集合；合法移动 = 纯函数。与数学文档的
  板型 B 同构，方形实例与 table_core 的 D4 规范形同源。
- **差分证据**：与现有方形引擎对拍——移动结果集合 34 个随机局面全等
  （5 种尺寸/等级组合，每组合计去重覆盖 ≥5 防塌缩）；规范形 120 例逐项
  相等 + 同块数 1045 对等价类划分一致；还原判定（含漂移 / 转置 / 翻面 /
  缺块）全等；捆绑组局面同样全等。
- **声名式机制**：锁死缝（`seam_clear` 钩子，米字 span 判据的落点）、
  冻形检测、可逆打乱（`safe_scramble`，3×2 上 40 步全部**精确**可逆，
  撤销路径反转 = 字面意义的解法）、形状可达性探针，全部与形态无关。
- **三维先例**：立方晶格 preset（dim=3、3 缝族、48 对称、m×n×d 还原态）
  **核心零行改动**——滑移 / 旋转还原 / 冻形行为与二维一致。
- **边界确认（诚实声明）**：引擎目前不动 game*.py / gui/ / solver/，main
  行为零变化；硬骨头 7/8/9（联合键 / orient 进规范形 / 对角缝朝向
  侧判定）已于 2026-10-21 解决，**米字 preset 随之落地并与 game_mi
  差分对齐**（`engine/mi_geometry.py`：×2 整数坐标 + A/B 双晶格 +
  5 邻表 + 四族 rank/span + SAT 重叠；测试 L 节证据——983 个合法
  移动在 game_mi 上逐一重放一致、移动结果集合互相覆盖、216 个侧
  分区全覆盖、还原判定 107 个变体一致、可逆打乱双重重放、重叠判定
  100² 对逐对一致）。**三角 preset 已于 2026-10-21 末落地**
  （`engine/tri_geometry.py`：斜坐标 Z² + up/down 三邻接 + 中心反演对称
  + 还原态 120°/240° 旋转轨道 solved_check；测试 M 节证据——703 个
  合法移动在 game_triangle 上逐一重放一致、移动结果集合互相覆盖、216
  侧分区全覆盖、还原判定含旋转轨道一致、可逆打乱双重重放）。另有两处
  与 game 的口径差异：`safe_scramble`
  的可逆候选遍历**全部**合法移动（game 只在同一条缝上遍历方向，故引擎
  可逆步更多、打乱更强）；`step` 定义域 ≥ 1（game 的 step=0 空转合法
  是怪癖，引擎显式拒绝）。

**风险提示**：用户预判「难度可能不亚于求解器开发」——调研支持这个判断：
真正的成本不在引擎核心（已验证轻量），而在 **GUI 层 60 处旗标分支的收敛**
与**求解器方形专用件的泛化决策**。因此路线图必须分期，每期独立可交付。

## 6. 附：引擎核心一页速查

```
板型 BoardSpec = (Lattice, directions, seam_families, orientations,
                  orient_dirs, goal_blocks, [seam_clear], [overlap],
                  [solved_check], [cell_polygon], [components], [seam_lines])
  Lattice      = (dim, scale, neighbor_steps, parity_linear, symmetry,
                  [orient_steps], [adjacency], [adj_periods])
                 # adjacency：显式邻接表（非正则密铺，碎三角）
                 # adj_periods：折叠周期基（查表邻接用）
  SeamFamily   = (name, coeffs, parallel, [rank], [line_scale])
                 # rank：朝向相关 side 钩子 (point, orient) → int（米字四族）
                 # line_scale：t = line_scale·L + 1（米字 h/v = 4，其余 = 1）
  components   可选钩子 (keys) → 连通分量元组。覆盖查表邻接——显式邻接
               板型的块一旦离开折叠基本域，查表就查不到邻居（碎三角按 1 个
               边长平移后 34–38 块落到残差表外）。几何共边判定与残差无关。
  seam_lines   可选钩子 (board, family) → ((t, line), ...)，该族在**当前
               局面**下的真实缝线（几何给线，不逐整数 t 枚举）。逐整数 t
               会把"线穿块内部"的 t 也算进来——那就是锯齿缝的来源。
局面 Board     = 不可变 Block(point, orient, group) 元组；
                 身份键 = (point, orient)（米字同格心 4 块靠朝向区分）
合法移动       = 选缝 σ → 一侧连通分量（捆绑组整组拖动）→ 平行方向平移 step 格
                 （逐步校验：不碰撞 / 每步后单一连通 / 两端非空；
                  同带多线只留最小 t 的代表——米字 ¼ 线同分区去重）
规范形         = 全部自同构（默认超八面体群：2 维 D4=8、3 维=48）× 平移归一取最小；
                 带朝向板型做 (point, orient) 联合变换（对称群含朝向置换）
还原判定       = 规范形 == 还原态规范形（旋转/翻面都算）；可挂 solved_check
规则自检       = locked_seams / frozen / shape_reachability / safe_scramble
```

⚠️ **`_sync()` 是缓存键的唯一刷新点——读键前必须先摸过 `self.board`**：
`solver/state.py:restore` 做搜索回溯时**就地改写** `b.location[i] = v`（不换块
对象，这是 2026-10-17 为省 25 万次 `Block.__init__` 刻意做的原地优化）。块上
缓存的 `engine_key` 就此过期。若 `opt` 在 `self.board`（触发 `_sync`）**之前**
读键，就会拿过期键去查新局面 → 判「选中块不在盘面上」→ 选中 0 块 → 求解器
收到 False → 报 `invalid_action`。

**症状极有欺骗性**：动作空间新旧完全同形（28 = 28），只是走出的解不同——方形
3×3 旧引擎 5 步解完、引擎卡在第 6 步；米字 14 步 vs 8 步。只比「能不能走」的
差分根本看不出来，必须比「同一局面跑同一个求解器给出的是不是同一条解」
（`test/_test_engine_gui.py` J 节）。

⚠️ 别想用「在 `_key_of` 里调 `_sync()`」一劳永逸：`_rebuild_blocks` 正在逐个
改写 location，中途 `_sync()` 会用**半成品指纹重建并覆盖 `self._board`**，把
正在读的新局面毁掉。正确做法是让调用点保证顺序（`opt` 里把
`keys = self.board.keys` 提到 `_key_of` 之前）。

⚠️ **性能：不许拿枚举器判成员（P3 收尾实测）**：`Board.legal_moves(step)`
枚举的是**整个合法移动空间**（缝 × 线 × 侧 × 连通分量 × 方向 × 逐步连通），
给求解器和 `has_legal_move` 用很合适，但拿它做「这一步行不行」的成员判定
（`move in legal_moves(step)`）等于每次把整棵树算一遍。实测 6×6 s2 打乱
**2777 ms/次**，cProfile 显示 98% 烧在 `legal_moves`（288 次调用 / 33.4 s、
1.16 亿次函数调用，`neighbors_of` 独占 894 万次）。修法两条：

1. `Board.can_slide(moved, direction, step, fam, t)` / `Board.slide(...)`
   ——**只校验这一次**的逐步碰撞 + 逐步连通 + 锁死缝 + 非全员，不枚举。
   `try_move_ex` 改走这里后 6×6 打乱 **25.9 ms**（经典引擎 14 ms，2.3×）；
   4×4 从 318 ms → 7.9 ms。`_test_shuffle_guard.py` 在引擎开启下从
   「>19 分钟跑不完」变成 76 s 全绿（2000 次打乱无终态命中死局黑名单）。
2. `Lattice.neighbors_of` 加记忆化（`_nbr_cache`，上限 2^18 条）+ 朝向表
   预建 `_orient_table`（原先每次调用都 `dict(self.orient_steps)`）。

配套的两条语义分野（`test/_test_engine_adapter.py` N7 节钉死等价性）：

- `can_slide` = **非严格**：只问「推得动、不断开」，允许选中片是任意子集。
  这正是 `try_move` 要的——连按两次方向键时，选中片不会因为贴上邻块而被
  撑大成新的连通分量，与旧引擎逐项一致。
- `Board.move_ok(move)` = **严格**：额外要求「选中片 = 缝某一侧的某个连通
  分量的捆绑闭包」，即 `legal_moves` 的完整语义，但只算这一条缝（2 次连通
  分量拆分，不枚举全树）。`compat.apply_action`（存档/宏回放原语）走它——
  回放层最怕静默容忍一个错动作，宁可多一次 BFS 也不能松。

性能护栏在 `test/_test_engine_gui.py` I 节：6×6 s2 打乱 20 次须在 8 s 内、
且与经典引擎相差 6× 以内（当前 2.6×）。它不是基准测试，只在快路径被整条
改回去时响。

⚠️ **编号谜题的 `numbered` 只能从 kind 派生（P3 可游玩观察期实测）**：
`puzzle_types.create_puzzle` 的引擎分支**提前 return**，走不到旧路径第 92
行的 `g.numbered = (kind=='numbered')` → 引擎下编号谜题矩阵值全变 1
（存档 / 成绩面板静默错，`update_matrix` 里 `numbered` 恒 False）。修法：
`EngineGame.__init__` 直接 `self.numbered = (kind == 'numbered')`。注意
GUI 的 `new_puzzle` 本来就显式 `self.game.numbered = numbered`，所以**真实
游玩路径没踩到**——这是直接调 `create_puzzle(kind='numbered') 的调用方才
暴露的（K 节回归两侧同测）。压缩存档回放（`_game_from_snapshot`）另走
SliderMatrix 直建，不受开关影响。

⚠️ **全局开关不许被测试顺手拨动（P3 实测）**：`config/engine.json` 是全局
开关，**任何**测试把它写成 true，同批并行跑的其它测试就全拿到 EngineGame，
「编号丢失」「形态判错」等假象一齐爆（实测一次污染把全套从 7 失败顶到
26 失败）。两个污染源都已堵：`_test_engine_gui.py` H 节把持久化重定向到
临时文件（且开机自清理——上一轮崩溃在 `_restore_config()` 之前会把 true
留给下一轮）；`_test_feature_index.py` 扫荡全部命令面板条目时**跳过**几何
引擎条目（产品行为是「拨过就记住」，测试不能替用户记住）。跑全套前先
`rm -f config/engine.json`。

⚠️ **侧判定（`side_of`）的精确等价式**：回放层 `_find_block_on_side` 按
形态分派到 `game_triangle.side_of` / `game_mi.side_of` / 引擎自带的
`EngineGame.side_of`。旧口径是 `gap_rank(key) <= line`；引擎侧的正确翻译是
**`rank_e <= line_scale·line`**（h/v：rank_e = 4×实数 rank、scale=4；
d1/d2：rank_e = 2×整数 rank、scale=1；方形 rank_e = r/c）。⚠️ 两个都别写：
①`rank_e < t`——整数线下等价，非整数线（d1 的 L=-2.5 这类）下
`rank <= -2.5`（⟺ <= -3）与 `rank < -1.5`（⟺ <= -2）判据不同，差分实测
60+ 处歧；②经 `_line_to_t`——其 `int(round(...))` 会把半整数线吞掉一半。
引擎自身枚举只产整数线（`all_gaps` 实测 0/30 非整数）故不致命，但回放层
线号来源不止一条。差分回归在 `_test_engine_gui.py` L 节（tri/mi 全族逐
¼ 枚举，约 3.6 万次判定零分歧）。

⚠️ **三角 rep 必须带朝向分量（P3 可游玩观察期修的产品 bug）**：
`gui/auto_solve.py:_handle_gather_result` 曾把三角动作的 rep 截成两分量
`(i, j)`，注释称「同格 ▲▼ 各一块、前两分量已足够」——**错了**：'n' 族缝
恰好从同格 ▲▼ 之间穿过（gap_rank：▲=i+j、▼=i+j+1，线 L=i+j 时 ▲ 在 0
侧、▼ 在 1 侧）。截断后回放层 `_find_block_by_cell` 按「盘面第一块」命中，
可能从错朝向起 DFS → opt 选错侧 → 整步被静默改写（现象：「解法播到一半
某步不可移动」）。经典引擎块序把所有 ▲ 排在前面，恰好一直命中对的那块；
几何引擎按键排序（down<up）后**必挂**（G7b 复现：2 分量 FAIL / 3 分量 OK）。
修法：三角与米字一样保留第三分量（`loc[:3] if (mi_mode or triangle_mode)`）；
回放层 `_execute_next_macro_step` 本就支持 `rep[2] if len(rep)>2`，legacy
两分量宏走首匹配（原行为不变）。

⚠️ **两套 shuffle 同种子不同态（设计差异，非 bug）**：引擎按**键排序**
重建块表（`_rebuild_blocks`），经典按创建序（三角先全部 ▲ 再全部 ▼），
`random.choice(self.blocks)` 于是选到不同块 → 同种子同次数打乱终态不同
（都是合法可逆打乱，分布等价——实测同批盘上两边求解行为逐盘一致）。
**影响面仅限「同种子复现」类测试**：`_test_tri_gui_solve.py` 的
`_gui_tri` 已改为「经典引擎造盘 → 喂给当前引擎」，把还原率指标与引擎
解耦（M4b 两侧均 7/8）。不追比特级复现——那要求引擎模仿经典的块序与
随机消耗序，收益为零、脆弱性极高。

⚠️ **两套真值的设计约束（P3 最大的坑）**：GUI 多条路径**直接写
`block.location`**而不经过引擎（动画落位写 `anim_end_pos` 且不调
`commit_move`、打乱演示整段重放、安全打乱回滚）。所以「引擎 Board 是唯一
真值」不成立——**块位置才是 GUI 眼中的真值**，引擎局面是派生视图。适配器
据此：`positions()` 直接读 blocks；每次进入逻辑方法先把 blocks 同步回
Board；`commit_move` 只在有 pending 时推进引擎。
