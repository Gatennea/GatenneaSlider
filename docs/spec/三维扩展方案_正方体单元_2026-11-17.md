# 矩形谜题向三维扩展方案（正方体单元）

> 2026-11-17 起草，讨论稿。**未认领、未排期、未改任何代码**。
> 当前游戏没有三维渲染（详见本文 §1.2），本文只做可行性 / 画面 / 接入顺序的讨论。

## 1. 可行性

结论先放前面：**规则层现成，渲染层和求解器层基本从头来。**

### 1.1 规则 / 数据层：现成

引擎的 `engine/registry.py` 已有立方板型 `cubic_spec(m, n, d)`：m×n×d 实心长方体为还原态，
6 邻接、3 个缝族（r/c/d）、48 种对称；`engine/lattice.py` 有对应 `cubic_lattice`。
源码注释明确写"核心对维度无感、零行改动"，`engine/board.py` 也把三维 preset 列为验证
"核心零改动延伸维度"的用例。

矩形谜题的 step（等级）只是移动参数、不进板型，所以三维版的规则就是同一套滑动沿三个轴走。
这一层不需要重新设计，只需要先与矩形规则做差分对拍，确认行为一致。

### 1.2 渲染层：从头写

现状是纯 2D：`gui/renderer.py` 里全是 pygame 的 `draw` / `blit`（数百处），
没有投影矩阵、没有深度缓冲；依赖里没有任何 3D 库（pygame-ce 的 SDL2 只用到 2D 部分，
numpy 服务于求解器与启动动画），也没有 3D→2D 投影函数。

"相机"是 2D 视野平移补偿（camera_x / camera_y），"着色器"是按位置分组涂色帮玩家还原，
两者都与 3D 无关——这几个词容易被误当成已有 3D 基础，特此澄清。

要做 3D，等距（斜四十五度）投影是成本最低的路线：小正方体堆成 m×n×d 长方体，
顶面 / 左面 / 右面三面同时可见，块间留缝，抽走块的位置露出凹坑（缺口）。
相机绕竖轴转四个角度、可缩放。

### 1.3 交互层：从头写

选块 → 选面 → 选缝 → 定方向的语义比二维多一维；现有拖拽跟随、缝隙命中容差、
点击吸附都是屏幕 2D 坐标，不能直接复用。深度排序与拾取（点到哪个块）也要新做。

### 1.4 求解器层：最难

查表数据（`solver/data/`）和宏 / 启发式（`solver/ml/`、`gap_solver.py` 等）全部按二维尺寸构建，
搬不到三维。更根本的是状态数按立方增长：二维 m×n 变三维 m×n×d，规模是乘积级上升。
这一层不能承诺二维那套速度和成功率，需要单独评估。

## 2. 实现后的渲染画面

目标形态（概念示意见对话中的配图）：

- 小正方体按 m×n×d 排列成大长方体，等距投影，顶 / 左 / 右三面可见。
- 相邻块之间留缝，缝要能看出深度；被抽走块的位置是凹坑，即待补的缺口。
- 每块按现有"分组着色"规律上色（位置 mod step），选中块高亮描边。
- 相机绕竖轴四档旋转、滚轮缩放；旋转只换观察角度，不改变盘面状态。
- HUD 沿用现有 2D 文字层（步数 / 时间 / 进度），贴在 3D 画面之上。

需要注意：本项目的防偏移方案（求解器侧消整体平移、回放按渲染位置逐帧补偿）是 2D 口径，
三维下相机的旋转 / 缩放与之叠加，要重新定义"整体平移"的含义，不能直接照搬。

## 3. 功能接入顺序

原则：**先把"没有求解器也能玩通"的闭环打通，求解器放最后。**
理由：三维状态数立方级膨胀、查表搬不过来；若先啃求解器，会卡在没有回归判据的真空里。

1. **规则底座（已现成）**：立方板型 + 与矩形规则差分对拍，确认核心零改动。
2. **等距渲染**：静态画面 + 相机绕轴旋转，不接任何输入，纯画面对拍。先看得见。
3. **可玩闭环**：选块 / 推块 / 打乱 / 还原判定 / 存档。不靠求解器也能玩通；
   闭环成立才有回归判据，后面每一步都靠它。
4. **求解器**：先接简单搜索，再谈查表 / 宏。放最后，且不承诺二维速度。
5. **周边功能**：分组着色 / 走步动画 / 音效 / HTTP API / 搭积木编辑器，
   都建在可玩闭环之上，按体验逐项补，不阻塞主线。

每阶段的验收都应落在可对比的产物上：对拍用集合 / 规范形比对，画面用截图，
闭环用可复现的走步序列，求解器用成功率与墙钟（二者同时报）。

## 4. 未决问题

- 三维缺口 / 孔洞的定义与可达性判定要不要沿用二维口径，还是另立规则。
- 打乱算法在三维下的安全性（打乱后仍在可解核）没有现成结论。
- 状态表示：坐标扩到 (r, c, d) 后，规范化和对称去重成本上升多少，尚未实测。
- 存档格式要不要扩字段、如何兼容二维存档。
- 是否引入真正的 3D 库实现自由视角，还是坚持等距四档旋转。
