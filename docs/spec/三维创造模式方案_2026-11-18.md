# 三維創造模式方案（正方體單元，2026-11-18 細化）

> **狀態：計劃，未認領、未改任何代碼。** 總方案 `docs/spec/三维扩展方案_正方体单元_2026-11-17.md`
> §5 第 5 階段只有一句「創造模式（三維搭建，參考 MC 的方塊放置 / 挖掘）」，
> §7 留了一句「參考 MC 的放置 / 挖掘判定與渲染（還未查公開資料）」。本文把那兩句展開成
> 可執行的判斷與步驟，不改總方案的結論。
>
> **為什麼現在寫**：豆包正在做三維核心（相機 / 測試），還沒碰創造模式；趁文件不交疊先把
> 計劃落定，等核心合併後按 `docs/agent/多AI协作与worktree.md` 認領施工。
>
> **定位（用戶原意，見 `docs/spec/設計訪談總結.md` §8）**：創造模式＝「允許拆開重裝、
> 還自動檢測能不能還原的魔方」，用來構造**即將復原時才會出現的簡單局面**——那正是最有
> 學習價值、卻很難靠隨機打亂碰到的狀態，對做新手教程價值最大。三維同樣吃這個紅利：
> 三維狀態空間更大，「只剩兩三塊」的局面更難碰上。

## 1. 現狀（已逐條核對代碼，不是猜）

| 已有 | 落點 | 對創造模式的用處 |
| --- | --- | --- |
| 立方板型 | `engine/registry.py` 的 `cubic_spec(m,n,d)` / `cubic_board`，還原態 = `m×n×d` 實心長方體 | 設計還原態的基準 |
| 按需重建局面 | `engine/adapter.py` 的 `apply_pattern(cells, groups)` / `set_goal_pattern(cells)` / `clear_goal_pattern()` | 放挖一塊就重建一盤；自訂還原態直接走這條 |
| 連通 / 凍形 / 還原判定 | 同檔 `is_single_connected(cells)`、`has_legal_move(step)`、`is_solved()`；`engine/board.py::canonical_key()` 對三維自動得 48 對稱 | 保存門與還原判定的現成判據 |
| 無損局面序列化 | 快照的 `engine_state` 鍵表 `[r,c,d,gid]`、存檔 `type:cubic`（`gui/file_ops.py`） | 局面存取不用新格式 |
| 點面拾取 | `engine/cubic_pick.py` 的 `hit_face` / `face_is_internal` / `neighbor_location` / `block_at_location` | 「點哪個面 → 在它的相鄰格放塊 / 挖掉這塊」的幾何現成 |
| 可見面與投影 | `engine/cubic_view.py` 的 `collect_faces` / `point_visible` / `build_scene` | 挖塊只能挖看得見的面；幽靈預覽走同一套投影 |
| 樣式格式 | `gui/design_styles.py` 的 version 2（kind + 尺寸 + `cells` / `groups` 完整位置陣列）已能裝 `(r,c,d)` 三元組 | 三維還原態樣式**不用新格式**，補 `kind='cubic'` 分支即可 |

**唯一的硬阻擋**：`gui/speedrun.py::mode_allowed` 在 `cubic_mode` 下對 `create` 直接回 `False`
（註釋明說「不擋住的話，模式開關會把玩家送進一個二維畫布」），`set_game_mode` 的文案是
「三維暫不支持創造模式（搭方塊在第 5 階段）」。**不能先放開判據再補編輯器**——那正是
「放開功能 ≠ 放開 UI 入口」的老坑；`toggle_game_mode` 的循環判據也共用 `mode_allowed`，
只改一處會出現「開關按了沒反應、但 set 能進」的分裂。

## 2. 做什麼：兩種設計對象，對齊二維的兩級入口

二維創造模式（`docs/spec/bandaged_mode.md` §交互）分「① 打亂狀態設計（手動構造 / 隨機生成，
造打亂局面）」與「② 還原狀態設計（格子畫布 / 搭積木，造還原態）」。三維照這個骨架，但
**內容大幅變簡單**：三維只有正方體單元，沒有形狀庫 / 朝向 / 晶格 / 劈塊那一套，
`engine/editor_geom.py` 的二維 basis 不擴充，搭積木就是「在容積內增刪單位立方體」。

- **① 打亂狀態設計**：直接在三維容積內放 / 挖方塊，造出一個局面當謎題。
  - **手動構造**：進去先還原態（當前局的 `m×n×d` 長方體或已載入的樣式），玩家挖 / 放，
    實時重建局面；存的就是一份局面（`engine_state`），不是樣式。
  - **隨機生成**：復用安全打亂，但候選動作要換成六向 / 三切面族，需實測確認
    （總方案 §7 已記）；三維求解器未接，不能像二維那樣「生成後求解確認」。
- **② 還原狀態設計**：拼出一個非長方體的自訂還原態，存成樣式（三維樣式），
  開局後 `set_goal_pattern` 把它設為還原目標。此處才需要「能否還原」的檢測（見 §3.4）。

**MC 借鑑的邊界**：只借「對著面放一塊 / 點一塊挖掉」的**編輯手勢**，不借第一人稱漫遊、
物品欄、重力、合成。相機仍是本項目現成的四元數 + 拖空白旋轉 + 滾輪縮放 + 平移
（總方案 §2.2），不另起一套。

## 3. 關鍵設計判斷（每條給結論和理由，不只列問題）

### 3.1 放塊 / 挖塊的命中

- **挖**：點中可見面 → 用該面的 `loc` 定位並刪掉那一塊；`hit_face` 已按畫家序取最前面，
  内部面（`face_is_internal`）本就點不到，不必另判。
- **放**：點中可見面 → 取該面的 `axis`/`sign`，用 `neighbor_location(loc, axis, sign)` 算出
  面外相鄰格；若該格已有塊就不能放。**注意軸映射**：引擎邏輯座標 `(r,c,d)` 對應世界
  `(X,Y,Z)=(c,d,r)`（見 `gui/renderer.py` 畫切面處），`neighbor_location` 返回的是邏輯座標，
  不要再手動換序。
- **幽靈預覽**：懸停時在待放格畫半透明立方體（走 `cubic_view` 投影 + 现有 Alpha 路徑），
  非法（越界 / 已有塊 / 放後不連通）時改警示色。別用真實走步做預覽——污染歷史。

### 3.2 單一連通與「可玩」保存門

- 編輯中途允許空盤 / 單塊 / 不連通（不然没法挖成兩半再攏回去）；**保存與開局**時才過門。
- 門的口徑對齊二維搭積木（`docs/spec/搭积木编辑器.md` §4）：**≥1 塊 + 單一連通 +
  ≥2 顆可動**（`has_legal_move(step)` 凍形檢測）。三維額外注意：**內部空腔不算不連通**——
  6 鄰接連通即可，玩法層本就不把空腔當連通缺陷（總方案 §1）。
- 自訂還原態也要過同一道門；否則存出來的「目標」本身凍住，開局即死。

### 3.3 「能否還原」檢測：只做必要條件，明確不承諾充分

用戶把創造模式定位成「自動檢測能不能還原的魔方」，但三維求解器排在最後、現在沒有，
所以**做不了完整可達性判定**。如實的做法：

1. 塊數等於某個 `m'×n'×d'` 實心長方體（遍歷合理因數組合，上限取當前容積）。
2. 各 mod 類 `(r%step, c%step, d%step)` 的計數與該長方體一致——step>1 時每類配額固定，
   挖多一塊少一塊立刻露餡。這是三維比二維更強的必要條件（step³ 組）。
3. 非空 + 單一連通 + 有合法步（§3.2）。

三條全過也只能說「沒被必要條件排除」，**不能說「一定能還原」**——三維存在死局，
完整判定要等求解器接上。UI 文案照這個口徑寫，別讓玩家誤以為過了門就有解。
`is_solved()` 對設定了 `goal_pattern` 的局面走 48 對稱規範形比較（旋轉 / 翻面都算還原），
與總方案 §1「認所有朝向、鏡像不單列」一致，**不用改**。

### 3.4 資料格式

- **局面**（①的產物）：直接存快照 `engine_state`（`[r,c,d,gid]`）+ `type:cubic`，
  `gui/file_ops.py` 已支援，不新增欄位。
- **三維樣式**（②的產物）：`gui/design_styles.py` 的 version 2 已經能裝——
  `kind='cubic'`、`m`/`n`/`d`/`step`、`cells=[[r,c,d],...]`、`groups=[[r,c,d,gid],...]`。
  要補的是讀取側：`annotation.py` 存樣式時只認 `triangle`/`mi` 兩分支（`exotic` 變數），
  `model_preview.py` / `session.py` 開局分派也要認 `kind='cubic'` 並把 `d` 傳進建局；
  別為三維另起一套樣式目錄。
- **捆绑（group）**：三維引擎層的 `group` 是維度無關的，但總方案把捆绑排在階段 5 與創造
  模式並列，**先不做捆绑**；樣式裡 `groups` 留空陣列即可，日後捆绑落地再接。

### 3.5 入口與模式隔離

- 沿用右下角模式開關 → 創造，二級只顯示三維可用的項（手動構造 / 隨機生成 / 三維搭建 /
  三維樣式庫）；二維的格子畫布、搭積木、二維樣式庫在三維態**不顯示**而不是顯示後拒絕。
- 放開 `mode_allowed('create')` 的時機 = 編輯器 Mixin 真正可用之後；放開時 `set_game_mode`
  的拒絕文案同步刪掉，並確認 `toggle_game_mode` 的循環判据跟著放開（兩處共用同一函数）。
- 造出的局切回練習 / 競速：競速初始局面已走 `engine_state` 無損鍵表（`_timer_initial_map`），
  三維已放行走這條，不用為創造模式另寫。

## 4. 實現步驟（每步有可看產物）

| 步 | 做什麼 | 可看產物 |
| --- | --- | --- |
| 0 | 純數據 / 邏輯層：容積內增刪塊 → 重建局面、連通 / 凍形 / 必要條件檢查。**不碰 `mode_allowed`** | headless 腳本能增刪並列印判據 |
| 1 | 編輯會話 Mixin（新建於 `gui/` 下，檔名施工時定）：進出會話、工具狀態（放 / 挖）、容積邊界、還原態 ``goal_pattern`` 讀寫 | 遊戲內能進一個只屬於三維的編輯會話 |
| 2 | 拾取與渲染：`hit_face` + `neighbor_location` 翻譯點擊、幽靈預覽、非法色 | 點面放塊 / 點塊挖塊肉眼可驗 |
| 3 | 保存門與必要條件檢測（§3.2 / §3.3）接到「存檔 / 開局」出口 | 凍形或不連通被攔並說明原因 |
| 4 | 樣式讀寫 + 三維樣式庫 + **放開 `mode_allowed`**（§3.5） | 存一個自訂還原態，從樣式庫開局能還原回去 |
| 5 | 隨機生成：安全打亂候選換六向 / 三切面族，實測可逆 | 生成的局都能回到還原態 |

> 步 1–4 反覆改 `renderer.py` / `events.py` / `adapter.py`，與 §五十四、§五十六 文件交疊，
> 按規矩一個 AI 串行推到底；步 0 可先 headless 獨立做。

## 5. 驗收（產物在遊戲內看）

1. **能造**：進創造 → 挖出一個「只剩兩三塊」的近乎還原局面 → 切回練習能接著玩完。
2. **能存能讀**：自訂還原態存成樣式 → 重進遊戲從樣式庫開局 → 還原判定命中（旋轉 / 翻面也算）。
3. **攔得住**：凍形、不連通、mod 配額不對的局面存不了，提示說得清是哪一條。
4. **隔離對**：三維態看不到二維畫布 / 搭積木；二維態看不到三維樣式庫。
5. **不越界**：容積外不放塊、已有塊的格子不重疊、挖不到被擋住的內部面。
