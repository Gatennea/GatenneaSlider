# 模型文件（静态定义板型）实施计划

> 2026-10-24 定稿。目标：**新增板型不再改 Python**，丢一个 JSON 进目录即可玩；
> 最终让玩家在游戏内用已有滑块拼装配置、保存成模型文件。
>
> 本文只描述要做的事与验收口径。已完成的碎三角改造见
> `docs/spec/GUI解释器化接入计划_2026-10-23.md` 的修订 R1。

---

## 一、目标与非目标

**目标**

1. 板型 = 数据：形状 + 放置 + 朝向 + 缝族 + 步长，全部可从文件读取。
2. 加载即校验：写错的模型在加载时报错，而不是给玩家一个玩不了的盘。
3. 原版四谜题**运行路径一行不动**（见「双后端」）。

**非目标**

- 游戏内自由画多边形（只从形状库选，避免出现无法密铺的自定义形状）。
- 把原版四谜题改成文件驱动（可另写文件做对拍测试，但不进运行时）。

## 二、两层文件

### 2.1 滑块库 `models/shapes.json`

只放**原子形状**（不能再拆成库内形状的）。组合形状（菱形、长方形、六边形）
交给自由捆绑，不占形状位。

顶点用**整数格坐标**声明，`basis` 把格坐标映射到平面（行向量，浮点只在
这一层出现）。一个模型只允许一套 basis，所有形状顶点在该 basis 下必须是整数。

```json
{
  "schema": "gatenna.shapes/1",
  "shapes": {
    "square": {"verts": [[0,0],[1,0],[1,1],[0,1]]},
    "tri":    {"verts": [[0,0],[1,0],[0,1]]},
    "right":  {"verts": [[0,0],[1,0],[0,1]]},
    "iso30":  {"verts": [[0,0],[1,0],[1,1]]}
  }
}
```

> 注：`tri` 与 `iso30` 在 basis `e1=(1,0) e2=(½,√3/2)` 下分别为边长 1 的正三角与
> 30-30-120 等腰；`square` 用 `e1=(1,0) e2=(0,1)`。同一模型内混用不同 basis 的
> 形状**不允许**，需要时由加载器报错。

### 2.2 模型定义 `models/<name>.json`

```json
{
  "schema": "gatenna.board/1",
  "name": "shatter",
  "title": "碎三角",
  "engine": "geometric",
  "basis": [[1, 0], [0.5, 0.8660254037844386]],
  "tiles": [
    {"p": [0, 0], "o": "1", "g": 0},
    {"p": [2, 0], "o": "2", "g": 0}
  ],
  "shapes": {"1": "tri", "2": "iso30", "...": "..."},
  "orientations": {"1": {"shape": "tri", "angle": 0, "mirror": false}},
  "seams": [
    {"name": "h",   "line": [0, 1], "step": [6, 0]},
    {"name": "d30", "line": [-1, 1], "step": [3, 3]}
  ],
  "view": {"rotate": 180, "mirror": false}
}
```

| 字段 | 含义 |
|---|---|
| `engine` | `geometric`（几何引擎维护，自带缝族/步长）或 `native`（原版板型 + 样式） |
| `basis` | 格坐标 → 平面的 2×2 行向量矩阵 |
| `tiles` | 放置表：位置 + 朝向标签 + 组号（`g` 省略 = 不捆绑） |
| `orientations` | 朝向标签 → 形状 + 旋转角 + 是否镜像 |
| `seams` | 缝族：线方向 + 步长（`line` 与 `step` 都用格坐标） |
| `view` | 仅显示层：`rotate` 0/90/180/270 + `mirror`（绕水平轴翻） |

`native` 模型不带 `seams`/`orientations`，改为引用原版板型
（`"native": {"preset": "mi", "style": "<样式名>"}` 之类），由原版路径接管。

## 三、定稿的设计决定

1. **原子形状**：库里只放不可再分的；组合形状用捆绑（60° 菱形 = 2 正三角）。
2. **步长作者写、引擎验**：加载时枚举合法候选（平移后仍严丝合缝），文件里的值
   必须在候选内，否则报错并列出候选。`step > 1` 必须逐格验中途位置。
3. **双后端**：原版四谜题永远走原版快路径；模型文件导入走几何后端（认慢）。
4. **新板型只支持箭头 + 两次触控**：键鼠 / 单次触控 / 虚拟键盘关死。
5. **方向字母不写进文件**：按落屏方向自动分配（因为只支持箭头）。
6. **`view` 走显示层**：不动数据，故不影响缝、步长、存档。
7. **不做自由画多边形**；六边形不是加形状能解决的（实测 408 候选全半路碰撞）。

## 四、加载流程

```
读 JSON → 结构校验（字段/类型/范围）
        → 形状解析（顶点 → basis → 平面多边形）
        → 朝向展开（标签 → (形状, 旋转, 镜像) → 多边形）
        → 放置表解析（去重、越界、组号）
        → 缝族解析（线方向 → rank 泛函；步长 → 候选校验）
        → 物理公理校验（见下）
        → 组装 BoardSpec → 注册进 registry
```

**物理公理（全部必须在加载期跑）**

| # | 公理 | 判据 |
|---|---|---|
| A0 | 还原态自洽 | 无重叠、单一连通、块数 = `tiles` 条数 |
| A1 | 缝是真缝 | 每条缝的线**整条**落在块边上，不劈开任何块 |
| A2 | 缝可滑 | 沿缝平移一个步长，途中每个中间位置都不重叠（逐格，不是只查首尾） |
| A3 | 每步可逆 | 任一步沿反方向能精确推回；两侧非空 |

任一条不过 → 抛错并指出「哪个字段 / 哪条缝 / 哪两块」。

## 五、存档

- `geometric` 模型局：快照存**稀疏 `tiles` 三元组**（`[p, o, g]` 排序），不存矩阵。
  理由：矩阵是包围盒的稠密快照，实测碎三角打乱一次就从 2098 字节涨到 4915 字节，
  而信息只有 48 个三元组。
- 存档头带模型身份：`{"model": {"name", "schema", "hash"}}`。hash 不一致 →
  只读打开并明确提示；模型缺失 → 直接拒绝，**绝不回退成方形**。
- 老五形态的 `matrix` 格式一行不动。

## 六、实施步骤

| 步 | 内容 | 验收 |
|---|---|---|
| S1 | `engine/geometry_ops.py`：把碎三角已有的通用算法抽出来（共边连通 / 缝线枚举 / SAT 重叠 / 形状→多边形） | 碎三角测试全过，行为零变化 |
| S2 | `models/shapes.json` + `engine/model_loader.py`（解析 + 组装 BoardSpec，先不做校验） | 能从文件造出与代码等价的碎三角 |
| S3 | 公理校验器（A0–A3）+ `validate_model.py` CLI | 故意写坏的模型全部被拒，且报错定位到字段 |
| S4 | 存档通用分支（稀疏 tiles + hash + 失败策略） | 走一步存读往返逐块一致；改模型后读旧档给出明确提示 |
| S5 | 注册与入口（启动扫描 `models/`，登记进 registry；`create_puzzle` 走通） | 新模型无需改代码即可建局 |
| S6 | 原版四板型各写一份文件**仅作对拍**（不进运行时） | 文件版与代码版 legal_moves / 还原态逐项相等 |

S1–S3 是「能读」的地基，S4–S5 是「能玩、能存」，S6 是 schema 表达力的证据。

## 七、已知风险

1. **坐标基不统一**：现有三套坐标并存（方形整数、米字半整数、碎三角各向异性
   scale-6）。模型文件自带 `basis`，加载器只认「整数格 + 一个 basis」，不再有第二套。
2. **朝向标签重映射**：`view.rotate` 若做成语义旋转，需要重映射全部朝向标签并重新
   校验；因此定为显示层变换。
3. **性能**：几何路径比整数键查表慢一个量级。加载后必须预计算邻接与缝线并缓存，
   不能每帧现算（旧教训：6×6 打乱 2777ms → 缓存后 26ms）。
4. **存档兼容**：缝族命名与线号口径一旦改动，旧档回放会错位，靠 `model.hash` 拦住。
5. **统计口径**：捆绑出来的形状在数学上是多个块（菱形 = 2 块），做可解率 / 上帝之数
   统计时要单独标注，不能与原版四谜题混算。
