# 内存开销排查（2026-11-12，待办 §三十六）

> 现象（用户原话）：平常 200MB 以内，偶然一次看到 700MB，无法复现，需要排查隐患。
> 本轮结论：**已复现、已定位、已给上限与释放点**。本文是这次排查的真源，
> 源码注释里的「见内存开销排查」都指这里。

## 一、怎么复现的

离屏（SDL dummy 驱动）起一个真实的 `SliderGUI(m=4, n=4, step=1)`，画 60 帧
空闲画面后，按默认自动求解的第一步依次调 `load_table`，每步用 `psutil`
读进程 RSS，同时开一条 50ms 采样的监控线程记峰值。一次性探针脚本未入库，
数据可按下节命令自行重跑。

| 步骤 | RSS | 峰值 | 说明 |
|---|---|---|---|
| GUI 空闲 | 138 MB | 138 MB | 与用户「平常 200MB 以内」一致 |
| `load_table(4,4,1)` | 613 MB | 613 MB | 一次 +475 MB |
| `+ load_table(4,4,2)` | 667 MB | — | |
| `+ load_table(5,5,2)` | **735 MB** | 735 MB | 用户看到的 700MB |
| 清掉缓存 | 141 MB | — | 回落到基线 |

关键：**这是常驻，不是暂态**。`_table_cache` 一直持有到进程退出。

各档实测体积（`dict[int, int]` 每条约 95 字节）：

| 档位 | 文件 | 条目数 | 常驻增量 |
|---|---|---|---|
| `4_4_1` | `checkpoint.pkl` 164 MB | 5,135,644 | +475 MB |
| `4_4_2` | `table.pkl` 18 MB | 559,504 | +52.7 MB |
| `5_5_2` | `checkpoint.pkl` 31 MB | 612,563 | +67.5 MB |

## 二、根因

`solver/table_solver.py` 的模块级 `_table_cache` 旧实现是「载入即永久缓存、
无上限、无释放」。而 `solver/auto_solver.py` 的第一步「①查表」是**无条件**
调 `table_solve` 的（不是只有玩家手动选「查表求解」才会走）。于是：

1. 玩家开一局恰好落在某个 checkpoint 档位（如 4×4 step1），点求解；
2. 第一步就把 164 MB 的断点表整体 `pickle.load` 成 5.1M 个 Python 对象；
3. 表被永久缓存，之后换局、切算法、求解结束都不释放；
4. 再点几个尺寸就叠到 700MB。

「无法复现」也由此解释：默认局面多半落在小表或无表的档位，只有个别尺寸/步数
才会撞上大断点表。顺带一提，`4_4_1` 按 `docs/solver/求解器優化方向_可行性判據.md`
的结论本来就是**不完整的断点表**（覆盖率低），花 475MB 常驻换来的候选命中率
很低，更不划算。

## 三、排除掉的项（别再当成本次根因）

- **背景没擦 / 关网格残影**：那是另一个待办（§三十七），与本轮内存无关。
- **开机动画 24 帧**：854×480 RGBA × 24 实测 **+38 MB**，确实常驻整个会话，
  但量级撑不到 700MB。已顺手修掉，见下节。
- **音频 / bgm**：`gui/audio.py` 走 `mixer.music` 串流，只存路径；
  §二十 已实测 +64.5MB → +0.08MB，不是隐患。
- **历史快照**：`history.py` 的 `history` 是唯一「随操作次数线性无上限」的持有，
  但 8×8 盘 2000 条快照实测只 +2.2 MB（约 1.1 KB/条）。要吃到 500MB 得几十万步，
  **不是本次 700MB 的元凶**。撤销/重做语义牵连广，本轮不动，只在采样通道里
  把条数记下来长期观察。
- **GUI 各处缓存**：箭头精灵、缝段、数字字体、点击反馈等都有容量上限或键空间有界；
  `op_log` 只写盘、`log_writer` 有 4MB 轮转。
- **每帧 `Font.render`**：是 CPU 热点（§二十二），不是内存持有。

## 四、修法

1. **表缓存加预算**（`solver/table_solver.py`）
   - `_table_est_bytes()` 按条目数 × 100B 估算，不遍历整表；
   - 单表 > 64MB **不进长期缓存**：返回的表只由本次调用的局部变量持有，
     `table_solve` 一返回就回收（对应「用完即释放」）；
   - 小表走 LRU，总预算 128MB，超出淘汰最久未用的档位；
   - 载入前若文件已比单表预算大，先 `release_table_cache()`，避免
     「已缓存小表 112MB」和「本次临时大表 475MB」叠成更高的峰值；
   - `release_table_cache(key=None)` / `table_cache_stats()` 作为显式释放与观测口。
2. **可选硬上限**：`GATENNEA_TABLE_MAX_FILE_MB`（默认 0=不限）。设置后超过
   该大小的 table/checkpoint 直接跳过，`table_solve` 返回 None → 自动求解落到
   下一候选。玩家若在意内存，可用它彻底避开单次载入的固有峰值。
3. **开机帧播完释放**（`GUI.py`）：`_run_boot_phase` 的所有退出路径 +
   `run()` 在重启跳过标题阶段时的兜底，都把 `_boot_frames` 置空，省 38MB。
4. **长时间采样通道**（`gui/mem_probe.py`）：默认完全关闭，不 import psutil、
   不起线程、不建文件。见下节。

### 修复后同一串操作

| 步骤 | 常驻 RSS | 峰值 |
|---|---|---|
| GUI 空闲 | 138.6 MB | 138.6 MB |
| 调一次 `load_table(4,4,1)` 并返回 | 140.4 MB | 613.0 MB |
| `+ 4_4_2`（进缓存） | 192.6 MB | 613.0 MB |
| `+ 5_5_2`（进缓存，合计 112MB 未超预算） | 261.0 MB | 613.0 MB |
| 再调一次 `load_table(4,4,1)` 并返回 | 142.5 MB | 613.0 MB |

常驻从 735MB 降到 261MB（且可一键 `release_table_cache()` 回到 142MB），
峰值从 735MB 降到 613MB；平常路径仍是 138MB，**没有回退**。

### 仍然存在的局限（如实留档）

613MB 峰值是 **pickle 一次性反序列化 164MB 文件、构造 5.1M 个 Python 对象**
的固有成本，不是缓存造成的。要把它也消掉，得把 `dist` 改成「按键排序的紧凑
数组 + 二分查找 / mmap」，运行期只占接近文件大小的内存。这要改存储格式、
改 `load_table` 的返回类型，并连带所有实验脚本（它们现在直接 `len(table)`、
`random.sample(list(dist), N)`），属另一轮工程，**本轮没做**。在此之前，
`GATENNEA_TABLE_MAX_FILE_MB` 就是给玩家的规避手段。

## 五、下次再看到 700MB 怎么办

打开采样，照平常玩，复现后看 CSV 里那一行 `SPIKE +xxxMB` 处于哪个阶段：

```
set GATENNEA_MEM_PROBE=0.5
set GATENNEA_MEM_PROBE_OUT=D:\mem.csv
```

- 进程一启动就建 CSV、每行立即 flush，**强杀进程也不丢数据**；
- 列：`t_s, rss_mb, phase, history_len, table_cache_mb, boot_frames,
  solver_running, shuffle_active, event`；
- `phase` 自动区分 求解 / 无限打乱 / 宏播放 / 动画 / 空闲；
- 单次涨幅 ≥32MB 自动记一条事件；`GATENNEA_MEM_PROBE_OUT` 不设时写到系统
  临时目录，启动时会打印具体路径；
- 未启用时 `maybe_start()` 只做一次环境变量读取，零内存、零线程。
